# 失败 Trace 04 rec_duplicate_request_blocked 判据无对话证据

- 用例 [packages/eval/src/cases/recovery.ts](../../packages/eval/src/cases/recovery.ts)
- 类别 recovery P1 判据要求客服解释「无需重复操作的原因」
- 修复状态 已修复 复验通过 39s
- 证据 `eval/failures/rec_duplicate_request_blocked-*.json` 共 4 轮导出 全败

## 失败轨迹

四轮失败形态一致 对话里顾客从未提出重复提交要求 判据无从验证
> 顾客: 你好 我想咨询一下订单 SO-2026-0009 的退款问题
> 客服: 请问您希望退款的具体原因是什么呢
> 顾客: 好的 我确认这些信息都对 我是因为不想要这个商品了 想直接退款
> 客服: 退款已为您成功办理 退款单号 RT-2026-0002 款项将按原支付渠道(微信)退回
> judge: 对话中顾客并未提出重复提交退款申请的要求 客服全程也未提及或解释无需重复操作的原因 无法核实该判据

## 根因分析

评测场景设计缺陷。用例意图是验证「客户要求重复提交退款时 客服解释系统幂等拦截无需重复操作」 但模拟器(Haiku 扮演顾客)执行剧本时丢弃了「请对方操作两次」的要求 只提出一次退款请求。判据与对话证据脱钩 judge 按规则「只依据 transcript 不得脑补」必然判不通过。

判据设计原则的代价:判据必须二元且可从 transcript 验证 这保证了评测可信度 但要求场景必须确实触发目标行为。场景强度不足时 判据就成为永远无法满足的空断言。

## 修复

强化场景剧本 让重复提交要求成为顾客的开场诉求:
- reasonForContact 「订单 SO-2026-0009 不想要了 要求退款并请对方操作两次确保到账」
- instructions 「开场即要求退款并请对方操作两次确保到账 若对方解释重复提交会被系统拦截无需重复操作 接受解释即结束」

修复后对话中顾客明确要求操作两次 客服解释系统拦截 判据有据可依。
