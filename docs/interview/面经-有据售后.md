# 面经：有据售后 AfterSales Copilot

这份面经面向 Agent 应用与全栈研发岗位。建议完成[导学](../learning/导学-有据售后.md)后按问题复练。主回答按约 60–90 秒组织，追问用于展开；实际时长取决于语速，不要求背诵内部函数名。第一人称仅表示解释方式，**不表示所有实现都由本人独立完成**。个人职责尚未确认，Q02 提供诚实的回答边界。

项目简介：有据售后是一个本地可复现的售后 Agent 工程项目。当前默认离线入口围绕仅退款和退货后退款，把自然语言交互与确定性业务执行分开，通过持久任务、资金执行权、事件投影和评测证据处理长流程及故障恢复。真实模型、真实支付与生产上线不能由当前材料证明。

## 项目事实与工程支柱

以下是项目层面的简历候选素材，确认个人贡献后才可以改成“我设计”“我负责”。具体数字、验证环境和职责核实表见[简历事实摘要](简历事实摘要.md)。

- **受控业务执行：** 针对模型输出不能直接成为资金授权的问题，将申请意图交给领域规则重新核验，再通过审批绑定、业务执行权与发送意图推进模拟退款；正式客户入口覆盖两类退款及等待阶段零资金验证。
- **持久恢复：** 针对请求结束、人工等待和进程退出导致的执行中断，持久化命令、任务与检查点，用租约代次拒绝旧执行者写回，并按原交易查询恢复不确定资金结果；已有命名故障窗口实验。
- **证据检索：** 针对政策来源难定位的问题，保存内容快照、片段偏移与来源，区分检索解释和领域终判；字符基线与 BM25 有固定小题集对照，未宣称已采用向量检索。
- **费用治理：** 针对并发与重试可能越过预算的问题，通过冻结配置、逐尝试预占和整数结算共用账本；未知费用及可能在途的并发占位在恢复后保留。
- **全栈一致性：** 针对断线、重复事件和身份切换后的迟到响应，使用持久事件游标、客户白名单投影与前端订阅隔离；客户公开进度由业务事实联合核验生成。
- **可追溯评测：** 针对汇总结果无法解释变化原因的问题，分别保存业务、协议、服务和 Judge 结果，关联源码、题集、配置及逐例证据；历史会话可生成 L1 草稿但必须显式采纳，离线测试与真实质量按不同口径报告。

## 业务与架构

<a id="q01"></a>
### Q01 项目解决什么问题，为什么值得做

**考察点**：能否从用户任务解释技术价值，并主动说明实际验证范围。

**口述回答**：我会用一次退款说明这个项目。客户只说“东西有问题，想退”，系统要先确认是哪笔订单、是否签收、是什么原因，再判断是否需要主管批准和客户寄回。这种输入不完整、查询顺序会变化的部分适合模型参与。但订单归属、退款金额和资金是否已经执行，不能依赖模型措辞判断。所以项目把对话和业务执行分开：模型提出工具调用，代码重查事实并受理持久任务，后台按照已核验方案推进。客户看到的进度来自业务记录和事件，而不是模型说“完成”就算完成。当前能展示的是本地离线的两类退款、审批和恢复机制；我不会把模拟通过率当成真实用户解决率，也没有线上处理量可以报告。

**追问：知识库足够完整后还需要 Agent 吗？** 知识库提供依据，但用户可能没有提供必要信息，查询也可能需要按结果继续。如果业务输入完全结构化、路径固定，我会直接采用表单和确定性流程。Agent 的价值要通过同一任务的规则基线、交互轮数、成功率和费用比较，不能从“用了模型”推出效率更高；当前项目尚无真实业务收益对照。

**追问：规则短路是否损害自主性？** 自主性需要定义在允许的任务范围内。模型可以决定先查什么、何时补问，却没有自行扩大退款额度或绕过审批的权力。把金额规则交给代码是在划定职责，是否还需要模型则由剩余不确定性决定。

**依据**：[第 01 章](../learning/01-项目全貌/01-售后业务与项目边界.md)、[第 08 章](../learning/04-Agent机制/08-Agent与确定性工作流的分工.md)、[当前装配](../../packages/runtime/src/compose.ts)。易错说法是“所有售后都自动完成”或“保证资金绝对安全”。

<a id="q02"></a>
### Q02 哪些是你负责的，哪些由 AI 辅助完成

**考察点**：职责可信度、设计理解与复盘能力。

**口述回答**：我会先把项目已有机制与个人贡献分开。代码里有持久任务、审批和预算账本，只能说明项目具备这些实现，不能直接说明都是我独立设计的。个人部分需要明确到某个需求、设计选择、实际改动和验证记录。如果有 AI 辅助，我会说明 AI 生成了什么初稿，我审查了哪些边界，又依据哪个失败现象作了实质修改。比如讲退款恢复时，至少应能解释原业务键为什么稳定、发送意图为何先落库，以及哪个实验确认恢复没有增加渠道提交。当前这套材料还没有核实我的具体模块归属，所以我可以先介绍项目方案和学习复现过程，不使用“独立负责全部核心架构”这种无法支持的表述。

**追问：没有提交记录就不能讲贡献吗？** 不必只依赖提交记录，但需要可以复核的事实。设计说明、差异、失败日志、修复后的断言以及本人能解释的决策都可辅助判断。仅仅读懂现有代码，不应改写成亲自实现；协作成果也不能整体归到一个人。

**追问：最难问题该选哪个？** 先选确实参与并能还原证据的事件。如果只做过复现，可说“我复现并分析了结果未知窗口”；如果确认参与修复，再讲修改。仓库已有无 Git 评测入口故障可作为技术复盘素材，不能自动称作本人经历。

**依据**：[事实与贡献核实表](简历事实摘要.md)、[来源清单故障及修复](../handoffs/p10-source-manifest-fix.md)。禁止补造团队人数、线上事故、用户量和节省成本。

<a id="q03"></a>
### Q03 一次客户请求怎样贯穿整个系统

**考察点**：能否说明模块输入输出、持久化边界与异步交接。

**口述回答**：我把这条链路拆成受理、对话、业务执行和展示。客户页面提交消息和请求键，API 验证身份、格式及资源归属，把命令和任务持久化后返回受理结果。会话 Worker 认领任务，用冻结配置调用模型，确认完整轮次后执行允许的工具。查询结果回填原工具调用；如果申请退款，领域服务重新检查订单、政策和金额，形成售后及业务任务。需要审批或寄回时就保存等待状态，不占住最初的 HTTP 请求。业务 Worker 获得执行权后调用独立模拟渠道，确认结果再补齐原工具结果与客户事件。页面通过 SSE 补发事件，并读取受控进度。所以 HTTP 已受理、业务已完成和客户已看到结果是三个不同时间点。

**追问：为什么不用一个长 HTTP 请求做完？** 审批可能跨越数分钟甚至进程重启，浏览器也可能关闭。连接只能表达通信生命周期，不能承担业务事实保存。受理后用稳定运行身份查询进度，才能把网络重试与后台推进分开。

**追问：模型已经回复成功，但退款没有成功呢？** 客户资金进度以业务、效果和执行权联合状态为依据。模型不应获得宣布资金成功的权威；投影失败应补事件，渠道未知应核验，不能统一重新执行整条链路。

**依据**：[全景时序](../learning/01-项目全貌/02-一次退款请求的全景.md)、[持久会话](../../packages/runtime/src/durable-conversation.ts)、[业务投影](../../packages/persistence/src/p6-conversation-refund.ts)、[演示证据](../experiments/p11-learning-validation.md)。

<a id="q04"></a>
### Q04 Agent、Workflow、ReAct 与计划执行怎样选择

**考察点**：选择依据是否来自任务依赖，而非框架名词。

**口述回答**：我先看下一步能不能在收到输入时完全确定。固定的金额和资格判断适合确定性工作流；需要根据观察继续查询或补问的部分适合 Agent 循环。这个项目的循环是模型提出工具调用，宿主执行并回填观察，然后进入下一轮，直到结束、等待、升级或达到上限。它具有行动与观察交替的特点，但不能因为没有显式输出思维链就说不是 Agent，也不需要向用户暴露内部推理。计划执行则更适合能够先拆出较稳定依赖的任务，执行中仍要验证计划是否过时。当前退款主线是受控循环加持久业务任务，P8 只是固定双分支调查，没有通用自动规划任意任务图的能力。

**追问：Planner、Executor、Critic 必须是三个模型吗？** 不必。规划可以由模型生成，执行交给代码，核验既可以是确定性规则，也可以在适合的主观指标上使用 Judge。增加角色会增加协议、延迟和费用，先确认职责确实需要独立上下文，再设计对照。

**追问：为什么资金步骤不让模型再规划？** 授权针对的是已核验方案。恢复时重新规划可能改变金额、业务身份和政策依据，原批准就失去了对象。已有资金意图的任务优先查询原交易。

**依据**：[第 08 章](../learning/04-Agent机制/08-Agent与确定性工作流的分工.md)、[第 19 章](../learning/06-交互与运行治理/19-有限双分支调查与运行记忆.md)、[编排扩展](../learning/08-扩展专题/扩展-编排协议与记忆.md)。

<a id="q05"></a>
### Q05 原生工具调用如何实现，怎样停止无限循环

**考察点**：理解工具协议、完整消息确认与停止条件。

**口述回答**：模型获得工具名称、描述和输入 Schema，返回的是带调用身份的工具意图，真正执行发生在宿主代码。宿主先验证协议、工具是否允许及参数，再把结果绑定到原调用，回填下一轮上下文。工具调用和工具结果必须成对，不能把结果当成一条无关联的普通聊天。在持久会话里，完整模型轮次和每个工具结果分别确认；半段参数流中断不会被保存成成功调用。停止也不只靠 Prompt：当前会话有最大轮数，Worker 有任务时限，网关有尝试和预算限制，协议错误会停止并提示核验。合法补问会进入等待，不应该为了凑出最终回答而一直调用模型。

**追问：一次输出多个工具怎么办？** 先检查协议是否声明允许以及输出是否合法，再按当前执行器的实际顺序处理。模型“并行工具能力”不等于宿主真的并行执行。副作用不能为追求速度而绕开各自授权和确认边界。

**追问：相同工具反复调用是否一定失败？** 不一定，新的证据可能合理改变查询。但没有进展的重复需要检测和限制。当前上限可防止无限循环，不代表已有完善的语义无进展检测；新增检测应区分合理回查和机械重复。

**依据**：[原生循环](../learning/04-Agent机制/09-原生工具调用与Agent循环.md)、[协议实现](../../packages/runtime/src/p7-protocol.ts)、[持久循环](../../packages/runtime/src/durable-conversation.ts)。易错说法是“模型直接调用后端函数”或“JSON 合法就可以执行”。

<a id="q06"></a>
### Q06 多轮澄清与上下文如何保存，压缩会不会丢事实

**考察点**：区分事件历史、模型上下文、检查点与记忆。

**口述回答**：我先保存能够重建对话的事实，再决定每次给模型看什么。项目把完整模型轮次、工具调用和结果存成事件，客户补充信息需要关联原来的补问调用，恢复后才能还原正确消息序列。任务检查点则记录哪一轮和哪个工具已经确认，作用是恢复执行，不是聊天摘要。仓库另有工作便签、旧工具结果裁剪和确定性压缩模块，但默认持久会话目前调用的是事件重建，并没有直接启用那套管理器。因此我不会说当前默认已解决长上下文问题。如果扩展压缩，需要保留订单身份、授权状态、原业务键、未决问题以及证据指针，并在压缩前后检验事实与工具配对是否完整。

**追问：摘要遗漏了旧事实怎么办？** 摘要不能成为唯一副本。应保存原事件或证据引用，按权限回读，再检查版本是否仍适用。模型生成的新摘要也不应覆盖已经核验的资金状态；执行时仍从业务系统读取。

**追问：短期和长期记忆有什么区别？** 会话上下文服务本次交互，运行记忆服务一次任务；跨会话偏好需要独立的来源、客户范围、有效期和冲突更新规则。P8 的运行投影不是长期客户画像。

**依据**：[上下文](../learning/04-Agent机制/10-多轮澄清与上下文管理.md)、[运行记忆](../learning/06-交互与运行治理/19-有限双分支调查与运行记忆.md)。易错说法是“数据库里存了聊天，所以已经有长期记忆”。

<a id="q07"></a>
### Q07 怎样限制幻觉和 Prompt Injection 的实际影响

**考察点**：是否把安全约束放在可信执行边界。

**口述回答**：我会把不可信输入与执行权限分开。用户文字和检索内容可以参与理解，但不能改变身份、角色、订单归属和审批条件。工具目录减少可选择动作，Schema 约束格式，执行时再校验资源和业务前置；这几层作用不同。旧 Runner 有查单后的动态工具门控，当前持久入口主要用冻结工具版本限制集合，不能混称同一实现。退款金额来自领域记录，渠道发送还要拿到业务执行权，所以即使模型被诱导输出退款意图，也不能仅凭那段输出完成付款。对客户的事件由服务端白名单构造，内部工具参数和诊断不直接透出。验证时要检查是否发生越权和资金动作，而不只是回答有没有拒绝措辞。

**追问：工具已经隐藏，为什么还要鉴权？** 工具隐藏只影响模型通常能看到什么，不能保护绕过模型的 API 请求或配置错误。可信校验必须在服务端执行入口，资金还要再次验证原授权。

**追问：政策文档写着“忽略系统要求”怎么办？** 将其当成待解释的数据，不能当作新指令。测试既要覆盖直接用户注入，也要覆盖工具或文档中的间接注入；当前离线安全用例的通过范围不等于面对任意真实模型都不会被诱导。

**依据**：[安全边界](../learning/04-Agent机制/11-工具门控与安全边界.md)、[客户投影](../../apps/api/src/customer-view.ts)、[客户事件测试](../../apps/api/test/customer-events.test.ts)。

<a id="q08"></a>
### Q08 项目的 RAG 从原文到引用怎样实现

**考察点**：是否讲清实际链路及未实现环节。

**口述回答**：项目先读取受控政策文章，按内容版本和分块配置构建稳定快照。分块优先保持段落，过长段落按窗口拆开，保存父文档、标题、原文偏移和版本。当前窗口是 320 个 UTF-16 单位，没有重叠，不能说成 320 token。查询时，默认持久客户入口使用字符关键词基线，按文档去重取前三条，返回可定位来源供模型解释。运行冻结了知识快照，不匹配时拒绝静默换版本。最后退款资格仍由领域代码读取订单、物流和规则判定。这里没有向量库、混合融合或模型重排，BM25 属于已有独立对照模块。引用存在只能证明出处可找到，还要另测它是否支持最终回答。

**追问：为什么不把全文都放进 Prompt？** 小语料可以把全文直塞作为基线，不必预设检索一定更好。比较需要同题、同模型、同版本，记录完整依据覆盖、回答忠实性、token 与延迟。当前项目没有完成这种真实模型对照，不能给出收益数字。

**追问：知识更新如何保证一致？** 当前做的是快照身份核验，不是成熟的多版本索引发布系统。若要无中断更新，应在旁路构建并验证新索引，原运行绑定旧版本，新运行切换新版本，并保留回退和授权过滤。

**依据**：[检索章节](../learning/04-Agent机制/12-政策检索引用与确定性判定.md)、[knowledge.ts](../../packages/domain/src/knowledge.ts)、[RAG 实验](../experiments/rag-baseline-v1.md)。

<a id="q09"></a>
### Q09 BM25、向量、融合与 Top-k 应怎样比较

**考察点**：指标、实验变量和选型依据是否匹配。

**口述回答**：我会先定位检索失败是什么。编号和条款关键词常适合词项匹配，同义改写可能需要语义检索；融合可以组合候选，但不会凭空补回两路都没召回的依据。这个项目实际比较的是字符基线和中文双字 BM25，没有实现向量融合。P4 保留集中，参与相关性指标的是十道有依据题，BM25 的 Recall@3 从 0.76 到 0.86，但 Recall@5 从 1.00 降到 0.95，所以不能总结成全面提升，也没有因此替换默认策略。Top-k 还影响证据容量、噪声和上下文成本：需要五篇依据的题，取三篇天然无法全覆盖。我的下一步会保持题集、语料和生成器不变，单独比较召回、重排与生成，避免多个变量一起变化。

**追问：融合为什么不能直接加原始分数？** 两个排序器的分数范围和意义可能不同。可以先做校准，也可以用排名融合降低量纲问题；倒数排名融合按名次加权，不是已经证明适合这个项目的方案。具体公式、去重与例子见扩展专题。

**追问：Chunk 和 overlap 怎样调？** 用固定标注题比较证据完整率、冗余与成本，不只看单条命中。规则表格要保留条件与表头，片段过短可能把例外条件切走，过大则带来噪声。现有短条款实验不能证明长 PDF 解析能力。

**依据**：[P4 原始报告](../../eval/rag/results/2026-09-25T14-11-43-679Z/report.json)、[检索扩展](../learning/08-扩展专题/扩展-检索生成与模型迁移.md)。

<a id="q10"></a>
### Q10 召回正确但回答错误，怎样定位

**考察点**：能否进行逐层归因，而非直接换大模型。

**口述回答**：我会先确认“召回正确”的定义。命中一篇相关文档，不代表所有条件都齐全；只保留局部片段，也可能漏掉金额或时间例外。随后检查真正进入模型的上下文，而不是只看检索日志，确认裁剪、版本和排序没有丢依据。如果证据完整且进入了模型，再看回答是否错误引用、忽略限制或添加无依据承诺。最后独立检查业务规则，避免把生成解释错误和退款资格错误混成一类。实验上可以固定检索结果，只替换生成提示；也可以给定标准证据看回答是否改善。当前项目有引用定位与检索指标，但没有当前真实模型答案忠实率，因此这些归因实验是后续方案，不能称为已经测得的效果。

**追问：RAG 和微调如何选择？** 经常更新且要追溯出处的知识优先外部检索；稳定输出习惯或特定任务行为可以讨论训练，但需要训练集、独立评测和成本依据。微调不是实时知识库，也不自动解决越权或资金恢复。

**追问：没有依据能否让模型常识补充？** 应区分一般解释和具体业务承诺。涉及客户资格或金额，应回查、补问或升级，不能用常识补出允许退款的结论。生成可读性与业务授权仍然是两层。

**依据**：[第 12 章](../learning/04-Agent机制/12-政策检索引用与确定性判定.md)、[第 20 章](../learning/07-验证与设计取舍/20-测试L1L2与Judge.md)、[检索与生成扩展](../learning/08-扩展专题/扩展-检索生成与模型迁移.md)。

## 资金、并发与恢复

<a id="q11"></a>
### Q11 幂等如何实现，退款超时为什么不能直接重试

**考察点**：区分请求去重、业务去重与外部结果未知。

**口述回答**：我会先确定三种身份。请求键保护一次 HTTP 受理，同键同参返回原运行；业务键表达同一笔退款，即使换会话也不能变成第二笔；渠道用稳定业务身份识别同一动作。真正发送前，系统在本地事务中校验授权、取得执行权并保存发送意图，之后才调用渠道。正常收到结果就确认业务；如果渠道已经执行但响应丢失，本地超时不能推出没退款。恢复看到原意图后优先查询同一业务键，确认成功再补本地状态，查询仍未知就保留待核验。当前模拟渠道与业务库独立，故障实验能比较提交和成功动作计数，但这不是任意真实支付系统全局恰好一次的证明。

**追问：发送意图刚写完就崩溃，实际上没发怎么办？** 恢复进程无法仅凭本地记录区分“尚未发”与“已发未确认”。当前采取保守查询和待核验。更主动恢复需要渠道提供明确幂等及查询契约，不能靠猜测清掉意图。

**追问：没有渠道幂等和查询能力呢？** 本地唯一约束只能限制本地受理，无法消除跨网络的不确定窗口。要改变业务协议、引入人工核验或设计可审计补偿，并明确重复和漏执行风险，不能声称加个锁就解决。

**依据**：[确认样章](../learning/05-资金执行与恢复/14-退款幂等与结果未知.md)、[资金仓储](../../packages/persistence/src/p6-task-repository.ts)、[客户故障实验](../../apps/api/test/conversation-refund-process.test.ts)。

<a id="q12"></a>
### Q12 审批如何防止重复决定和授权丢失

**考察点**：事务边界、方案绑定与等待期执行权。

**口述回答**：批准不是资金完成，也不是无限次执行许可。服务端要把主管决定绑定到原运行、售后、金额和最新断点，用条件更新保证两个相反决定不能互相覆盖。决定与执行意图同事务提交，避免点击成功但进程退出后无人继续。消费一次性凭据时，又把授权消费和持久命令受理放在同一事务，失败一起回滚。退货后退款还要等待寄回和收货，批准阶段只接管未发送的执行权，不能立即付款；收货核验原关联后，把仍处于未发送状态的持有者转绑到收货命令。如果已经发送或未知，收货不能生成第二次许可。这样人工等待跨进程存在，批准对象也不会被悄悄替换。

**追问：前端禁用按钮够不够？** 不够，多个页面、重试和直接 API 调用都可能竞争。真正的唯一胜者由数据库前置条件与受影响行数确定，界面只改善操作体验。

**追问：审批过期能不能直接释放资金状态？** 审批时限和外部发送事实不同。可能已经发送的动作需要查原交易，不能因时钟到期推定未执行。拒绝或过期处理同样要核验业务尚未进入不可随意撤销的阶段。

**依据**：[审批章节](../learning/05-资金执行与恢复/13-从售后申请到审批与执行.md)、[审批原子性实验](../experiments/approval-atomicity.md)、[执行权转绑](../../packages/persistence/src/p6-owned-after-sale.ts)。

<a id="q13"></a>
### Q13 租约到期后旧 Worker 返回，为什么不能继续写

**考察点**：并发控制与围栏的保护对象。

**口述回答**：仅有到期锁可以允许接管，但不能让旧执行者立刻消失，所以需要执行代次。任务认领在写事务里核算配额并更新所有者、代次和租约期限。新 Worker 接管时代次增加，旧响应回来时，检查点、完成和资金准备写入都再次验证当前所有者、代次、状态和期限；不匹配就拒绝。心跳负责续租并传播取消，检查点保存已确认步骤，二者不互相替代。并发上限约束的是有效租约数量，不代表单进程已经启动同样数量的线程。对于外部退款，围栏保护本地确认仍不够，还要保留业务执行权和发送意图，因为旧请求可能已在外部生效。

**追问：为什么检查和写入必须同事务？** 如果先读取资格、退出事务后再写，接管可能发生在两者之间。必须让资格核验与业务写回共享受控事务，网络调用则放在事务外，避免持锁等待外部服务。

**追问：CAS 和 SQLite 锁是什么关系？** 条件更新表达“只在预期状态仍成立时修改”，事务和数据库锁提供并发提交基础。它不是一个内存布尔锁，也不能从单库多连接测试推导已完成多节点生产部署。

**依据**：[租约章节](../learning/05-资金执行与恢复/15-Worker租约与检查点.md)、[认领与围栏](../../packages/persistence/src/p6-task-repository.ts)、[进程竞争测试](../../packages/runtime/test/p6-process.test.ts)。

<a id="q14"></a>
### Q14 关闭页面、调用失败、进程退出分别怎么恢复

**考察点**：错误分类和恢复动作是否匹配。

**口述回答**：我会先看丢失的是连接、执行资格还是外部结果。页面关闭只影响展示，重连补发事件，不重新退款。模型协议失败要保留原调用和费用信息，由网关限制尝试，不能在每层都重试。只读工具未确认时可以按协议重新读取，但新数据可能变化，需要版本判断。Worker 退出后，新进程领取原任务并复用已确认检查点。资金已经可能发出时，只查询原交易。业务成功但客户事件没写完，则补投影，不再执行资金。因此恢复实验需要在受理、模型响应、业务受理、支付响应和投影等明确窗口退出，然后联合检查原关联、渠道计数和事件。只演示一次重启，不能证明所有窗口正确。

**追问：取消之后为什么还有成功退款？** 取消本地等待不等于撤销已经执行的外部动作。应先确认真实资金事实，再停止后续工作；任务取消和业务已成功可以表达不同层面的事实。

**追问：人工接管能直接结案吗？** 接管是沟通责任变化。结案仍要检查未知资金、未完成任务和缺失关联；聊天里说“已处理”不能替代渠道结果。当前没有完整真实渠道对账系统。

**依据**：[故障窗口表](../learning/05-资金执行与恢复/16-跨进程恢复与人工核验.md)、[结案阻塞](../../packages/domain/src/case-closure.ts)、[客户进程实验](../experiments/p6-conversation-refund.md)。

## 全栈与运行治理

<a id="q15"></a>
### Q15 SSE 重连怎样补发，又怎样防止客户数据串线

**考察点**：传输游标、公开投影、前端生命周期是否完整。

**口述回答**：事件先保存到数据库，SSE 按原运行的序号读取游标之后的内容，重连只补事件，不重执行业务。客户只能收到服务端白名单重新构造的字段，内部隐藏事件保留原序号；如果一批全被隐藏，用水位帧推进游标，所以序号跳跃不一定是丢数据。前端按运行和序号忽略重复，订阅由身份和运行共同确定，旧连接清理后迟到回调不能更新新页面。普通请求还要处理切换后迟到的响应，选择版本比只比较运行 ID 更可靠，因为用户可能离开又回来。终态事件和传输结束也分开：服务端追平尾部后发送完成帧，客户端再关连接，避免看到业务完成就截断最后消息。

**追问：直接用最后一条消息的数组下标当游标呢？** 不行，过滤、去重和分页都会改变可见数量。游标应来自服务端稳定事件身份；客户端也不能据跳号推定未收到的内部事件必须公开。

**追问：为什么还查进度快照？** 聊天事件与业务进度关注点不同。快照核验退款、售后、资金效果和执行权，防止一条文案提前宣布成功。事件重放解决连续展示，快照提供受控的当前业务视图。

**依据**：[第 17 章](../learning/06-交互与运行治理/17-SSE事件投影与前端状态.md)、[服务端流](../../apps/api/src/sse.ts)、[客户工作台](../../apps/web/src/components/customer/CustomerWorkspace.tsx)、[重连测试](../../apps/api/test/p6-sse-reconnect.test.ts)。

<a id="q16"></a>
### Q16 模型预算为什么要预占，换模型有什么风险

**考察点**：并发费用、不确定用量和配置兼容性。

**口述回答**：事后统计只能告诉我花了多少，阻止不了并发请求同时透支。所以项目在调用前，用冻结的价格、上下文上限和输出上限计算保守预占，在同一事务里检查共享预算和并发槽。主 Agent、子 Agent、模拟用户和 Judge 共用预算，不能每个用途重新领取一份。每次供应商尝试独立记账，完整 usage 才结算实际费用；超时或断连无法确认用量，就保留未知预占，必要时也保留并发槽。重启不把它清零。换模型则还涉及工具协议、停止原因、参数增量、usage 和取消行为，不能只换名称。当前正式入口仍为 simulation，已有契约测试不等于真实供应商兼容或真实价格验证。

**追问：为什么不按输入字符数预占？** 字符与 token 不等价，估计还可能漏掉协议和输出。当前采用声明上界比较保守，代价是可用额度偏紧；真实接入需要核实上界与计费契约。

**追问：超时后切备用模型是否安全？** 必须区分模型调用和资金动作。先保留原费用风险与运行身份，明确允许的错误及回退规则；不能通过换模型重建一笔已可能发出的退款。当前没有可宣称的真实多模型自动回退实测。

**依据**：[预算章节](../learning/06-交互与运行治理/18-模型预算与费用账本.md)、[账本](../../packages/persistence/src/p7-ledger.ts)、[模型迁移扩展](../learning/08-扩展专题/扩展-检索生成与模型迁移.md)。

<a id="q17"></a>
### Q17 多 Agent 如何传递结果，部分分支失败怎么办

**考察点**：依赖、结构化证据、局部恢复与成本对照。

**口述回答**：项目的 P8 是固定两个调查分支，分别处理订单物流和政策，并不是任意自动规划。父子任务受理时冻结相同证据，保存客户、订单、版本和哈希，分支使用受限输入与结构化输出。确认结果时既核对引用，也核对自身租约和父任务状态。父流程确定性汇总，遇到冲突、失败或未知资金给出人工核验建议，不发起退款。已经确认的分支可以复用，不因另一边失败全部重跑。运行记忆保存本次事实和未决问题，不是跨客户长期记忆。已有串并行实验使用模拟调用和人为等待，可以证明调度、归因和局部失败协议，不能把本机耗时差写成真实模型质量或成本提升。

**追问：A 后并行 B、C、D，D 失败时 E 怎么办？** 如果 E 必须依赖三者，B、C 已确认结果保留，只处理 D；若业务允许不完整输出，E 必须显式标记缺失并限制动作。输入版本改变则要重新判断哪些结果仍有效。这个通用 DAG 是扩展设计，不是 P8 已有四分支能力。

**追问：并行工具少但 token 更多，算更高效吗？** 不能只挑一个指标。分支重复上下文、结构化输出和汇总都可能增加 token；应在同任务和同质量约束下同时比较延迟、费用、调用数与失败率。

**依据**：[P8 正文](../learning/06-交互与运行治理/19-有限双分支调查与运行记忆.md)、[对照证据](../experiments/p8-fixes.md)、[编排与记忆扩展](../learning/08-扩展专题/扩展-编排协议与记忆.md)。

## 评测、选型与交付

<a id="q18"></a>
### Q18 测试、L1、L2 分别证明什么

**考察点**：成功定义、数据来源及分母是否诚实。

**口述回答**：单元和集成测试检查规则、接口、事务和协议的明确性质；进程实验额外检查内存丢失后的恢复。L1 用固定脚本模型驱动既定轨迹，更适合回归宿主能否正确执行、拒绝和治理动作。L2 通过模拟用户多轮交互，任务路径更不确定，需要保存对话才能区分 Agent、模拟用户和服务失败。项目历史有全仓 692 项通过和单轮 L1 124 条通过，这是不同对象，不能相加成问答准确率。正式离线 L2 也只是协议和治理验证，历史真实模型成绩有不同版本与条件，不能代表当前版本。面对面试指标问题，我会先交代输入、成功断言、分母和日期，再给结果。

**追问：工具调用路径必须唯一吗？** 不应该机械要求唯一。应验证必要动作、禁止动作、参数和最终业务事实，允许等价正确路径。安全场景里正确拒绝且未发生副作用也可能是成功。

**追问：如何避免只挑好题？** 保留固定题集、难度与失败类型，说明标签争议和排除规则。不能在失败后删除环境错误再只报告漂亮分母；小型构造集也不能代表生产分布。

**追问：一次失败会话怎样变成回归用例？** 可以从该 run 的事件生成 L1 草稿，用户回合和工具轨迹按事件还原，夹具默认 baseline，必须人工指定编号后才写入 `regression`。这不是在线评测，也不是自动改 Prompt 或政策。夹具对不上时草稿重放失败，说明还要核对数据，而不是 L1 失效。会话还可以导出为 OTLP JSON 做离线对照，没有接入外部追踪平台。

**依据**：[评测正文](../learning/07-验证与设计取舍/20-测试L1L2与Judge.md)、[用例集](../../packages/eval/src/cases.ts)、[会话转草稿](../../packages/eval/src/trace-extract.ts)、[P9 修复实测](../experiments/p9-fixes.md)。

<a id="q19"></a>
### Q19 Judge 怎么校准，Pass@k 与连续全过有什么区别

**考察点**：机评可靠性、指标定义与空样本处理。

**口述回答**：Judge 适合补充解释完整性等主观判据，但不能推翻数据库中客观的退款结果。首先要验证它返回完整结构、正确判据和布尔值，超时要取消并等待本地收尾，拒绝迟到结果。其次还要用独立人工标注校准，检查分歧具体发生在哪种判据，而不只看一项总一致率。当前真实校准尚未完成，合成标签只能检验统计函数。稳定性指标也要分清：至少一次成功关注多次机会能否碰到正确路径，连续全过关注每次是否可靠。项目实现了按同一用例跨轮全部通过的指标；三轮中只有一轮成功，不能拿至少一次成功来声称单次稳定。

**追问：100% 就说明可靠了吗？** 先看分母和样本来源。部分兼容计算在零样本时会返回 1，正式解释必须结合分母，零观察应视为无证据；置信区间也不能修复偏科数据集或保证样本独立。

**追问：业务成功但 Judge 不通过怎么报告？** 分别保留业务成功率、主观判据与综合通过，不能悄悄改变分子。报告中的失败类型可能重叠，分类计数也不能相加冒充独立失败数。

**依据**：[指标实现](../../packages/eval/src/metrics.ts)、[Judge](../../packages/eval/src/judge.ts)、[校准实现](../../packages/eval/src/p9-calibration.ts)、[证据索引](../learning/维护与证据/核心结论与证据索引.md)。

<a id="q20"></a>
### Q20 本地怎么演示，备份与 Docker 验证有哪些边界

**考察点**：可复现操作和运行环境边界。

**口述回答**：演示使用独立临时目录，业务库和模拟渠道库分开，显式启动 simulation 和本机随机端口。脚本从正式客户入口申请，主管审批、客户寄回、操作员收货都走接口，检查受理重放、越权拒绝、等待阶段没有资金提交和最终渠道计数。随后停止写入者，使用 SQLite backup 分别导出两库，核对清单哈希并恢复到新空目录，再验证成功及未知状态保持。两次备份不自动构成跨库原子快照，所以停写是前提。当前本机正式进程演示已有证据，但 Docker 镜像、原生模块、卷权限、信号收尾和容器浏览器链路仍待验收；写了 Compose 不能等同部署已通过。

**追问：只复制 app.db 为什么可能不够？** 活跃 WAL 中可能有已提交数据，而且渠道事实在另一库。即使单库备份完整，两库采样时点不一致也会破坏联合状态，应使用已约定的停写和备份协议。

**追问：镜像里没有 Git 怎么归档评测来源？** 当前构建保存受控内容清单，运行时核验实际文件；缺失或不匹配拒绝评测，不伪造 clean HEAD。这证明内容身份，不是供应链签名。

**依据**：[精确命令手册](../runbooks/p11-local-offline-demo.md)、[本次文档演示](../experiments/p11-learning-validation.md)、[来源修复](../handoffs/p10-source-manifest-fix.md)。

<a id="q21"></a>
### Q21 为什么没有直接用 LangGraph、消息队列或 Redis

**考察点**：能否说明取舍及迁移代价，不贬低替代方案。

**口述回答**：当前目标是把少量高风险售后流程在本机做成可复查闭环，原生循环让工具协议和确认边界直接可见，SQLite 让命令与任务可以同库提交，也降低外部设施要求。代价是需要自行维护编排、协议适配和调度，不应该说框架没有恢复能力。LangGraph 有状态、检查点和恢复机制，是否采用要看团队是否需要更复杂任务图与生态。引入队列后仍要处理数据库提交与消息投递的一致性，Redis 缓存也需要权限、版本和失效规则。迁移前我会先测量瓶颈，再验证原来的授权、幂等、围栏和证据协议能保持，而不是因为面试题提到了这些组件就补上。

**追问：如果用 LangGraph，State 放什么？** 可以放运行身份、证据引用、已确认步骤、未决问题和业务状态引用，避免复制整库或保存密钥。节点输出是状态更新，合并规则需要明确；资金真实状态仍以业务库为准。此为迁移方案，项目没有使用 LangGraph。

**追问：框架检查点是否解决付款恰好一次？** 检查点保存执行进度，但外部完成与本地确认之间仍可能有空窗。需要稳定业务键、发送协议及渠道核验，不能用框架名称代替这些设计。

**依据**：[设计取舍](../learning/07-验证与设计取舍/22-设计取舍局限与迁移条件.md)、[编排扩展与官方资料](../learning/08-扩展专题/扩展-编排协议与记忆.md)。

<a id="q22"></a>
### Q22 Function Calling、MCP、API 和 Skill 有什么区别

**考察点**：能否区分模型表达、宿主执行、协议接入与过程知识。

**口述回答**：Function Calling 描述模型如何表达调用意图，API 是服务暴露的操作接口，MCP 标准化应用与外部能力的发现和调用，Skill 则组织可复用任务说明、资源和脚本。这些可以配合，但不是同一层。模型选择某个工具后，宿主验证权限和参数，再由本地函数、普通 API 或 MCP client 执行，结果回填模型。MCP 的 Host 管理客户端，Server 提供能力，并不因为协议标准化就自动拥有业务授权。Skill 可以描述先查订单再看政策的调查步骤，真正允许哪些工具仍由宿主约束。当前售后项目使用自有工具契约，没有实现 MCP 服务或业务 Skill 运行器；开发时使用技能也不等于产品支持技能。

**追问：如果接 MCP，第一步做什么？** 先选受限只读能力，定义输入输出、客户范围、超时和审计，再建立宿主到服务端的身份传递与服务端校验。不要把通用数据库写工具直接暴露成退款接口。

**追问：Skill 写了不准付款是否足够？** 不够。文字提供过程约束，真正的支付能力应在执行边界限制。即使加载了错误技能或返回内容含注入，也不能扩大工具权限和客户数据范围。

**依据**：[协议与技能扩展](../learning/08-扩展专题/扩展-编排协议与记忆.md)、[当前工具实现](../../packages/runtime/src/durable-conversation.ts)。这道题主要是扩展知识，不是已有集成经验。

<a id="q23"></a>
### Q23 Prompt 如何迭代，AI Coding 如何证明修改有效

**考察点**：是否具备可复查的诊断、变更与验证过程。

**口述回答**：我先保存失败输入、版本、模型轨迹和最终业务事实，判断错误属于知识缺失、工具不可见、参数问题、规则错误还是表达问题，再选择修改位置。Prompt 修改应有一个明确假设，用固定样本比较并保存失败，不把多项变化后的成功都归因给一句提示。AI Coding 也类似：先读需求与现有实现，定义可观察验收，再做有限改动，检查差异，运行能解决当前不确定性的验证。仓库的无 Git 评测入口故障就是可复盘材料：本机通过并不能证明镜像入口可用，修复需要内容来源清单及正式 HTTP 回归。这个事件属于项目证据，是否由本人实施另行确认。没有运行的 Docker 或真实模型实验不会写成通过。

**追问：效果突然下降怎么排查？** 固定失败输入，比较代码、模型、Prompt、政策、数据和服务配置，再逐层看召回、上下文、工具与判定。先区分协议或服务失败，再谈能力退化；不能第一步就不断增加 Prompt。

**追问：所有测试绿了还要 review 什么？** 检查测试是否覆盖用户要求和真实失败边界，是否只验证 mock，是否把错误状态当成功，以及文档是否夸大范围。静态检查、业务测试、进程恢复、视觉和目标环境验收各有对象。

**依据**：[P10 独立审查](../handoffs/p10-acceptance-review.md)、[修复交接](../handoffs/p10-source-manifest-fix.md)、[P9 比较协议](../../packages/eval/src/p9-report.ts)。

<a id="q24"></a>
### Q24 从零设计企业 Agent，会先做什么，重做又会改什么

**考察点**：能否按风险和证据推进，而非堆叠组件。

**口述回答**：我会先限定用户、任务和成功事实，尤其确认哪些操作有不可逆副作用。第一版只做一条核心流程，定义身份、资源归属、状态和业务键，再接模型查询与补问。需要跨等待时引入持久任务，出现外部不确定性时建立发送与核验协议，随后完善预算、事件投影和固定评测。企业环境还需要真实认证、渠道契约、容量、审计、监控和运维责任，不能把本机项目直接称为生产平台。如果重做当前项目，我会优先统一历史与持久路径的能力说明、补真实协议和目标环境验收，再根据失败数据决定检索升级或调度迁移。选型由约束触发，每增加复杂度都要能说明它解决了哪个已观察问题。

**追问：先做真实模型还是先做安全机制？** 两者可以分层推进，但真实模型验证不能绕开授权和费用边界。当前任务中真实入口仍锁定，不能为了面试完整擅自解锁。离线机制通过后，另定真实实验预算、样本和终止条件。

**追问：哪些能力现在无法证明？** 真实解决率、生产可靠性、真实多模型回退、通用 DAG、长期客户记忆、完整移动端体验和 Docker 实际运行不能由现有离线材料替代。可以提出验证方案，但必须与已有成果分开。

**依据**：[第 22 章](../learning/07-验证与设计取舍/22-设计取舍局限与迁移条件.md)、[当前限制](../../LIMITATIONS.md)、[渐进重建练习](../learning/09-练习与自测/渐进重建练习.md)。
