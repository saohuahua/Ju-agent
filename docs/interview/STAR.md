# 面试叙事 STAR

按 STAR 结构组织讲法 每一条都能在仓库里指到具体文件 拒绝无法验证的数字

## Situation 售后是资金与体验的双重成本中心

电商售后不只是客服问答 它连接订单 物流 政策 支付四个系统 处理的是退款这类不可逆副作用
人工处理的痛点 政策规则多且易错 旺季峰值人力贵 重复退款是真实资金事故
通用自动化方案不可行因为例外场景需要人的判断 于是问题变成
如何让 Agent 自动完成标准化售后 同时保证副作用绝对安全 可审计 可恢复

## Task 构建可评测 可恢复的售后 Agent 平台

目标拆成四条

1. 业务闭环 查单 退货 换货 退款 取消 升级六类流程全部可自动执行
2. 副作用安全 幂等 审批 断点恢复 重复提交拦截 纵深防御
3. 可观测 SSE 事件流 时间线 审计 每一步可追溯
4. 可评测 数据库终态断言的评测集 通过 P0 门禁阻断退化

## Action 关键设计与实现

### 混合架构 模型决策与确定性执行分离

- Agent 只输出五种结构化形状 tool_call clarify action final escalate
  由 Zod 严格校验 packages/agent/src/agent.ts
- 模型可见工具只有四个只读查询 白名单写进输出契约的枚举
  packages/contracts/src/agent.ts
- 副作用由确定性工作流执行 工作流不信任模型查询结果 自行重查
  packages/workflow/src/engine.ts

讲法 模型擅长理解和异常路径 资金安全必须由代码保证 这个边界是整个系统的地基

### 三道幂等防线杜绝重复退款

- 幂等键由业务身份确定性生成 执行成功落记录 重试入口短路
- 一次性审批令牌 大额路径必验 消费即失效
- 支付网关按幂等键去重 作为最终兜底
  packages/domain/src/services/after-sale-service.ts

讲法 at-least-once 投递加幂等执行等于效果上的 exactly-once
这不是理论 是两条 P0 用例每次提交都在验证的事实

### SSE 事件溯源与断线补发

- 事件先落库再产生副作用 run 内单调 sequence
- Last-Event-ID 重连从事件表续传 刷新后全量归约重建
- 前端纯函数 reducer 从事件推导状态 不依赖内存
  packages/contracts/src/events.ts apps/web/src/lib/runReducer.ts

### 四层确定性评测体系

- 32 条任务契约 八类风险面 每条含夹具补丁 冻结时钟 脚本模型 故障计划 断言集
- 数据库终态 轨迹 参数 网关扣款四类断言 无主观打分
- P0 门禁失败 CI 非零退出
- Pass^k 稳定性指标 生产 Agent 不能靠碰运气
  packages/eval/src/cases

讲法 评测是这个项目的一级功能不是附属品
评测首轮就抓到一个真实缺陷 领域服务在乐观锁下连续更新会版本冲突
内存仓储测不出来 SQLite 实现暴露了它 这正是终态断言的价值

### 环境受限下的技术决策

- 无 Docker 所以 SQLite 优先 仓储接口隔离 附 PostgreSQL DDL 迁移路径
- 不引入 Redis 用数据库租约表实现执行互斥 语义等价 少一个运维依赖
- 自研轻量 Agent 循环而非直接上 Mastra 为了完全掌控结构化校验 轨迹事件化与离线确定性
  docs/adr/DECISIONS.md

讲法 每一条都是权衡 不是不会用那些东西 是判断在当前约束下什么最合理

## 高频追问与回答要点

为什么用 Agent 不直接写 Workflow

- 用户的表达是不完整的 多轮澄清 意图识别 异常解释这些非结构化环节 Workflow 表达不了
- 但副作用路径全部固化为 Workflow 两者是互补不是二选一

为什么不用 LLM Judge 判成败

- 判定模型可以生成看起来正确的回复 但数据库状态骗不了人
- 资金安全必须有确定性证据 Judge 只用于回复质量抽样

重试如何避免重复退款

- 幂等键三道防线 at-least-once 加幂等等于 exactly-once
- 用例 rec_crash_resume 与 rec_duplicate_request 常态验证

Pass@k 和 Pass^k 的区别

- 一个是能力上限 一个是稳定性 生产看 Pass^k
- 脚本模型下两者恒等 真实模型下分离 分离幅度就是模型的稳定性

成功率提升来自哪里

- 评测报告按模型 提示词 代码三元组归档 对比实验可以归因
- 不预设结论 先跑实验再说话

模型被注入攻击了怎么办

- 白名单让模型语法上无法表达副作用调用 审批令牌只在服务端流转
- 安全用例故意让脚本模型扮演被攻陷的弱模型 系统层依然拦截 这叫纵深防御

## 数字诚实声明

当前 32/32 与 Pass^3 100% 是脚本化模型下的系统正确性证明
它证明的是运行时 工作流 工具 治理层的正确性 不代表真实模型的成绩
真实模型成绩需要配置密钥后跑 anthropic 模式获得 简历中两者必须分开表述
