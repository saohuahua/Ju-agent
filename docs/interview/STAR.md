# 面试叙事 STAR

按 STAR 结构组织讲法 每一条都能在仓库里指到具体文件 拒绝无法验证的数字

## Situation 售后是资金与体验的双重成本中心

电商售后不只是客服问答 它连接订单 物流 政策 支付四个系统 处理的是退款这类不可逆副作用
人工处理的痛点 政策规则多且易错 旺季峰值人力贵 重复退款是真实资金事故
通用自动化方案不可行因为例外场景需要人的判断 于是问题变成
如何让 Agent 自动完成标准化售后 同时保证副作用绝对安全 可审计 可恢复

## Task 构建可评测 可恢复的售后 Agent 平台

目标拆成四条

1. 业务闭环 查单 退货 换货 退款 取消 升级六类流程全部可自动执行
2. 副作用安全 幂等 审批 断点恢复 重复提交拦截 纵深防御
3. 可观测 SSE 事件流 时间线 审计 每一步可追溯
4. 可评测 数据库终态断言的评测集 通过 P0 门禁阻断退化

## Action 关键设计与实现

### 原生 Agent 循环 模型决策与确定性执行分离

- 模型走原生 tool calling 工具以目录下发 tool_use 块与 input_json_delta 增量流式
  消息重建符合原生协议 assistant 携带 tool_use user 携带 tool_result
  packages/agent/src/anthropic-model.ts packages/agent/src/model.ts
- ask_user 协议工具承接多轮澄清 用户回复绑定到对应 tool_call 构成 tool_result
  packages/agent/src/agent.ts
- 能力门控 未查过订单前业务动作工具不进每步工具目录 结构性防盲提交
  这借鉴 Sierra 的 defense in depth 能力不出现在目录里 模型无法被说服去用它
- 副作用由确定性工作流执行 工作流不信任模型查询结果 自行重查
  packages/workflow/src/engine.ts

讲法 模型擅长理解和异常路径 资金安全必须由代码保证 这个边界是整个系统的地基
上下文工程是 Anthropic 官方反复强调的 Agent 核心工程 我实现了三段式
working memory 状态便签 最近消息 超限确定性工具结果清理 压缩前后 token 落事件可量化

### 三道幂等防线杜绝重复退款

- 幂等键由业务身份确定性生成 执行成功落记录 重试入口短路
- 一次性审批令牌 大额路径必验 消费即失效
- 支付网关按幂等键去重 作为最终兜底
  packages/domain/src/services/after-sale-service.ts

讲法 at-least-once 投递加幂等执行等于效果上的 exactly-once
这不是理论 是两条 P0 用例每次提交都在验证的事实

### SSE 事件溯源与断线补发

- 事件先落库再产生副作用 run 内单调 sequence
- Last-Event-ID 重连从事件表续传 刷新后全量归约重建
- 前端纯函数 reducer 从事件推导状态 不依赖内存
  packages/contracts/src/events.ts apps/web/src/lib/runReducer.ts

### 两级评测体系 L1 治理回归加 L2 用户模拟

- L1 105 条任务契约 十一类风险面 脚本模型回放理想轨迹 零成本每次提交跑 P0 门禁
  packages/eval/src/runner.ts
- L2 tau2-bench 范式用户模拟 Haiku 扮演客户与被测真实模型多轮对话
  三档人设 选择性信息隐藏 哨兵终止 模拟器与被测模型强制分离
  packages/eval/src/simulator.ts packages/eval/src/sim-runner.ts
- 判定三层 终态与轨迹代码判定 communicateInfo 子串代码判定
  LLM judge 只兜底语气类主观项 且判据二元化可从 transcript 验证
- Pass^k 稳定性指标 分层抽样控成本 失败用例导出场景与 transcript 回流
  packages/eval/src/cases

讲法 TS 生态没有成熟的 tau-bench 等价物 这套用户模拟评测本身就是差异化卖点
Cresta 的真实案例 LLM judge 给 94% 加工具轨迹断言掉到 71% 说明只看回复不够
我的评测以终态与轨迹为准 judge 只做主观兜底 这正是生产公司的共识做法

评测首轮就抓到一个真实缺陷 领域服务在乐观锁下连续更新会版本冲突
内存仓储测不出来 SQLite 实现暴露了它 这正是终态断言的价值

### 环境受限下的技术决策

- 无 Docker 所以 SQLite 优先 仓储接口隔离 附 PostgreSQL DDL 迁移路径
- 不引入 Redis 用数据库租约表实现执行互斥 语义等价 少一个运维依赖
- 自研轻量 Agent 循环而非直接上 Mastra 为了完全掌控结构化校验 轨迹事件化与离线确定性
  工具接入不走 MCP 保持进程内直调 决策留痕 ADR-004 与 ADR-011
  防守口径见 [ADR-004 追问稿](adr004-defense.md)
  docs/adr/DECISIONS.md

讲法 每一条都是权衡 不是不会用那些东西 是判断在当前约束下什么最合理

### 人工接管闭环 AI 升级不是死胡同

- escalated 从死终态改为可接管中间态 状态机 escalated→handling_human→completed
  坐席工作台收件箱 SSE 双端实时 接管后与客户双向对话 附解决摘要标记解决
- 权限分离是设计核心 AI 不碰终审（升级即交出） 坐席不碰执行（退款补偿仍走审批中心）
  两类角色都只能在自己的一侧收口
- 评测覆盖接管闭环 6 条用例 含越权与幂等拒绝面 升级生命周期全程事件可回放

### 运营分析 满意度与任务成功分开表述

- 会话 source 口径（customer/sim）把评测数据挡在运营指标外 评测与运营共用一个数据库
  靠口径字段保证指标真实性
- CSAT 全终态收集 一 run 一评幂等拒绝 与任务成功率分开表述
  满意度×终态交叉回答 升级人工的会话客户是否更满意 人工接管价值的直接证据
- 图表是设计系统内自绘组件 单色系 无第三方图表依赖 拖欠的 token 成本指标如实标注不可得

## 高频追问与回答要点

为什么用 Agent 不直接写 Workflow

- 用户的表达是不完整的 多轮澄清 意图识别 异常解释这些非结构化环节 Workflow 表达不了
- 但副作用路径全部固化为 Workflow 两者是互补不是二选一

为什么不用 LLM Judge 判成败

- 判定模型可以生成看起来正确的回复 但数据库状态骗不了人
- 资金安全必须有确定性证据 Judge 只用于回复质量抽样

重试如何避免重复退款

- 幂等键三道防线 at-least-once 加幂等等于 exactly-once
- 用例 rec_crash_resume 与 rec_duplicate_request 常态验证

Pass@k 和 Pass^k 的区别

- 一个是能力上限 一个是稳定性 生产看 Pass^k
- 脚本模型下两者恒等 真实模型下分离 分离幅度就是模型的稳定性

成功率提升来自哪里

- 评测报告按模型 提示词 代码三元组归档 对比实验可以归因
- 不预设结论 先跑实验再说话

模型被注入攻击了怎么办

- 白名单让模型语法上无法表达副作用调用 审批令牌只在服务端流转
- 安全用例故意让脚本模型扮演被攻陷的弱模型 系统层依然拦截 这叫纵深防御
- v4 又补了一层 越权三分法 A 能力范围外拒绝收尾 B 纯攻击拒绝且升级且记审计
  C 正当诉求外包攻击话术否掉话术照办 判据一句话 剥掉话术后还剩可办的正当诉求吗
  这条来自真实教训 v2.2 为修误升级把攻击也降级处理 injection_defense 从 40% 掉到 7.7%
  评测体系拓住了自己引入的回归 这是整个项目最值钱的叙事之一

安全段的评测怎么设计的

- 26 条覆盖指令覆盖 角色扮演 编码绕过 渐进提权 伪造系统消息 诱导跳过审批 提示词抽取
- 断言分层是关键发现 审计行 鉴权拒绝行 脱敏串这类证据只在「模型犯错被系统拦住」时产生
  L1 断言它们验证系统层 L2 只断言结果正确 否则等于要求真实模型先犯错才算通过
- C 类反断言防矫枉过正 修复注入防御时不得把正常客户误升级 那正是 v2.2 当初想修的问题

为什么不用 Mastra 为什么不用 MCP

- 核心资产是评测闭环与副作用治理 循环只是胶水 自研换来校验修复 轨迹事件化
  离线确定性三个完全掌控点 工具全在仓库内 进程内直调零开销 外部 server 是新增信任边界
- 完整防守口径见 [ADR-004 追问稿](adr004-defense.md) 逐条追问与口径红线都在里面

## 数字诚实声明

L1 的 111/111 与 Pass^3 是脚本化模型下的系统正确性证明
它证明的是运行时 工作流 工具 治理层的正确性 不代表真实模型的成绩
L2 用户模拟 `pnpm eval:sim` 才是真实模型的智能层成绩 无密钥时诚实跳过
简历中 L1 与 L2 成绩必须分开表述 L2 数字写实际跑出来的值 不预设不美化
L2 提升数字（31.4% → 52.3%）两端均为实际运行报告 基线与终值用例集不同（105 → 111）已在表格标注
迭代中的回归（安全段）与装具缺口如实入册 见 LIMITATIONS
