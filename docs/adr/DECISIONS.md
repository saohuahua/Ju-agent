# 架构决策记录 ADR

本文件记录项目的关键技术决策 每条包含背景 备选方案与后果
面试中被追问"为什么这样设计"时 每条决策都能从这里找到答案

## ADR-001 单仓 Monorepo 与内部包直引源码

背景 多包系统需要共享契约与领域类型 任何割裂都会造成类型漂移

备选

- 单包分层目录 简单但边界靠自觉 无法物理隔离
- 多仓发布 npm 包 隔离最好但本地联调成本高 一个人维护不现实
- pnpm workspace 内部包直接指向 src/index.ts 免构建消费

决策 采用 pnpm workspace 十个包 contracts domain persistence tools workflow agent runtime eval api web
内部包通过 exports 指向 TypeScript 源码 由 tsx vitest next 在消费侧统一编译

后果

- 依赖方向被 package.json 物理化 上层想绕过分层会直接解析失败
- 免去每个包的构建产物与 source map 配置 代价是发布前需要引入打包 这对本项目不构成问题

## ADR-002 SQLite 优先 附 PostgreSQL 迁移路径

背景 目标开发环境没有 Docker 无法本地运行 PostgreSQL 而评测要求每条用例秒级重置环境

备选

- 要求安装本机 PostgreSQL 开发门槛高 评测夹具重置慢
- 纯内存对象 不落库 则"数据库终态断言"这个核心卖点不成立
- SQLite 单文件或内存库 事务与唯一约束语义完整 夹具重置毫秒级

决策 领域只依赖仓储接口 persistence 提供 SQLite 实现
SQL 约束与 PostgreSQL 同语义 唯一键 事务 条件更新
生产迁移路径 infra/postgres 提供 DDL 仓储接口保证可替换

后果

- 评测每条用例独立内存库 32 条用例全量三轮约 3 秒 这是评测可反复跑的前提
- 需要诚实说明 SQLite 与 PostgreSQL 在并发写入上的差距 本项目单写者模型下不构成问题

## ADR-003 不引入 Redis 与 BullMQ 用数据库租约表实现互斥

背景 调研建议 Redis BullMQ 做长任务队列 但引入它们的前提是分布式部署

分析 单节点下队列真正要解决的是两件事 任务不丢 任务不被并发重复执行
前者由断点表保证 后者由 leases 表的条件更新保证 TTL 到期可被接管
两个语义在 SQLite 中都已实现 引入 Redis 只会增加一个必须运维的服务

决策 首版不引入 Redis 工作流执行互斥走 leases 表
横向扩展时用 Redis 发布订阅替换 SSE 轮询 队列替换为 BullMQ 接口不变

后果 本地零外部依赖即可全功能运行 这本身就是环境受限下的工程判断

## ADR-004 自研轻量 Agent 循环 而非直接上 Mastra

背景 调研推荐 Mastra 作为运行时 但也强调"首版保持克制"

分析 本项目的核心资产是评测闭环与副作用治理 而不是框架集成
自研循环需要完全掌控的三件事 结构化输出校验与修复 轨迹事件化 ScriptedModel 离线确定性
框架的抽象层会遮住这些细节 且离线脚本模型在框架内很难做对称实现

决策 实现 provider 无关的 ChatModel 接口 双实现 ScriptedModel 与 AnthropicModel
模型只输出五种结构化形状 由 Zod 严格校验 非法输出走一轮修复
工具接入同样保持进程内直调 不走 MCP 见 ADR-011

后果

- 评测与真实模型共享同一套提示词与运行时 评测结论可迁移
- 面试可以讲清楚循环的每一步 而不是"框架帮我们做了"

## ADR-005 Agent 与确定性 Workflow 的边界

背景 模型擅长理解意图与处理异常 但不能承担资金类副作用

决策 边界按风险切分

- 模型可见的工具只有四个只读查询 工具白名单写进输出契约的 Zod 枚举 模型在语法层面就无法表达副作用调用
- 退款 取消等动作模型只能产出 intent 与 slots 由确定性工作流执行
- 工作流不信任模型的查询结果 每次执行前自行重查订单
- 高风险路径由一次性审批令牌把关 令牌只在服务端流转 模型永远接触不到

后果 纵深防御成立 即使模型被注入攻击完全攻陷 能造成的最坏后果是一次查询失败

## ADR-006 SSE 事件溯源与断线补发

背景 工作台需要实时时间线 且刷新后状态必须与服务端一致

决策 事件先落 agent_events 表再产生副作用 SSE 从表补发
事件携带 run 内单调 sequence UNIQUE 约束兜底
客户端 Last-Event-ID 重连 服务端从该序号之后续传 UI 用纯函数归约器从事件重建状态
message.delta 提供流式观感 message.completed 为重放权威

后果 任何时刻刷新页面都能无损重建 单节点用轮询追增量 简单可靠

## ADR-007 幂等键与 at-least-once 语义

背景 网络重试 进程中断 人工重复点击都可能导致退款执行两次

决策 三道防线

- 幂等键由业务身份确定性生成 refund returnNo
- 执行成功立即落幂等记录 后续重试在入口短路
- 支付网关 mock 本身按幂等键去重 即使记录丢失也不会二次扣款

at-least-once 投递 加 幂等执行 等于 exactly-once 效果 这由 rec_crash_resume 与 rec_duplicate_request 两条 P0 用例持续验证

## ADR-008 评测四层 不让 LLM Judge 决定成败

背景 业内大量 Agent 项目只测回复文本相似度 无法回答"钱退对了没有"

决策 评测以确定性证据分层

- 第一层 数据库终态断言 判定退款金额 状态 审计唯一来源
- 第二层 工具轨迹 必选 禁止 有序子序列 参数精确匹配
- 第三层 系统可靠性 故障注入 断点恢复 重复副作用 网关扣款次数
- 回复质量留待 LLM Judge 但不参与成败判定

P0 用例失败直接阻断 CI 脚本套件全量三轮约 3 秒 具备每次提交都跑的条件

## ADR-009 时钟注入与冻结

背景 政策时限判定依赖当前时间 直接取系统时间会让评测不可复现

决策 领域全部依赖 Clock 接口 评测用 FrozenClock 冻结在夹具锚点 2026-09-20T12:00:00Z
审批过期用例通过时钟快进触发 状态机与政策边界因此可以精确到毫秒验证

## ADR-010 演示环境令牌认证

背景 需要区分客户 专员 主管三种身份验证权限模型 但本项目不做认证系统

决策 演示令牌写死映射 客户令牌绑定客户号 操作员与主管令牌走环境变量
越权检查是真实的 属主校验在工具层与领域层双重执行并有审计
替换为正式认证只需要换掉 auth.ts 的令牌解析 其余不变

## ADR-011 工具接入不走 MCP 保持进程内直调

背景 社区主流方案用 MCP 接入工具生态 但本项目的工具全部位于仓库内部

分析 MCP 的价值在于跨进程工具接入与生态共享 本项目工具是 contracts 包内的
Zod 契约加 tools 包内的进程内函数 没有外部工具服务器需要接入
引入 MCP 的代价 独立进程与 stdio/SSE 传输增加运维面 JSON-RPC 包装与内部
契约之间多一层转换 轨迹事件化要求每个工具调用的入参与结果逐 token 落事件表
跨进程边界使这一步多一层序列化 离线确定性要求 ScriptedModel 与真实模型对称
MCP 工具还需额外做脚本化适配 且外部 server 是新增信任边界 攻击面扩大

决策 首版工具全部进程内直调 模型只见由 Zod 契约生成的 JSON Schema
接入外部工具生态时再评估 MCP 作为候选 当前 ChatModel 与 ToolDefinition
抽象即迁移点 新增工具只需在 contracts 登记契约 tools 注册实现

后果

- 工具调用轨迹与评测断言共享同一进程内实现 事件表可精确重建每一轮
- 攻击面收窄 无外部 server 信任边界 白名单即最终权限边界

## ADR-012 前端依赖从零新增转为受控引入

背景 v1-v3 坚持 apps/web 零新增运行时依赖 图表全部自绘 SVG 动效只用 CSS 过渡
v4 要做落地页级滚动动效与运营驾驶舱多图表联动 手写这两类代码的成本已经超过收益

分析 自绘 SVG 图表在 analytics 页已证明可行 但那是四张静态图
驾驶舱需要时间轴刷选 图例联动 响应式重排 自绘等于重写一个图表库
滚动进场 视差 数字递增三类动效若用 CSS 与 IntersectionObserver 手写
需要自己处理 reduced-motion 降级 卸载清理 与 React 并发渲染的时序

决策 受控引入两个前端依赖 边界写死

- framer-motion 承载滚动进场与数字递增 只用声明式 API whileInView 与 animate
- recharts 承载驾驶舱与分析页的联动图表 配色由 console-charts.tsx 统一注入
- 边界 只允许出现在 apps/web 后端八包保持零新增运行时依赖不变
- 自绘 SVG 组件 charts.tsx 保留 特殊图形 如三道防线闸门 泳道时间轴 继续自绘

后果

- 放弃"全栈零新依赖"这一叙事 换取前端开发效率 这是明确的取舍不是疏忽
- 两个库都支持 prefers-reduced-motion 但不自动生效 降级逻辑仍需显式编写
- recharts 默认浅色 深色控制台需统一封装 避免每处单独配色漂移

## ADR-013 前台浅色后台深色的双轨主题 用区域语义而非用户偏好

背景 本产品同时服务两类人 客户在前台提交售后诉求 运营与工程在后台看系统真相
单一主题下这两类界面长得一样 无法从视觉上区分谁在看 看的是什么

备选

- 全站浅色 现状 前后台无区分
- 全站深色 客户侧界面压抑 不适合安抚情绪的售后场景
- Tailwind dark: 变体 语义错误 dark: 表达的是用户偏好 prefers-color-scheme
  而这里需要的是区域语义 同一个用户在同一偏好下 前台该亮后台该暗

决策 同一 sage 色相两个面 用 data-theme="console" 作用域切换

- 前台 /workbench /my 沿用既有浅色 token 客户侧保持安抚感
- 后台 驾驶舱 坐席 审批 分析 运行 评测 沙箱 固定深色控制台
- 侧边栏属于外壳 恒为深色 进入前台时主区域切浅 深浅交界即前台后台的视觉证据
- 不提供用户切换开关 主题由路由决定 区域语义不接受用户覆盖

后果

- 组件不得写死颜色 一律走 CSS 变量 由 data-theme 作用域决定取值
- 每个跨轨复用的组件要在两轨各验一遍 这是双轨的确定成本
- 深色轨所有文本组合必须过 WCAG AA 实测对比度表见 docs/redesign-audit.md
