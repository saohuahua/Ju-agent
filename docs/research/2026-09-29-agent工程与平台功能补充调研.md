# aftersales Agent 工程能力与平台常用功能补充调研

调研日期：2026-09-29

与[上一轮调研](2026-09-28-智能客服竞品与功能补充调研.md)的关系：上一轮从产品与竞品出发，给出人工协作、技能目录、客户进度、坏例回流、换货履约等产品化方向。本轮换一个切面，从 Agent 工程基建与平台常用功能两个方向重新对照业界现状，重叠项会显式标注为「与 0928 调研同向」，避免重复建设。两轮结论不互相覆盖。

## 结论

这个项目在副作用治理、持久恢复、离线评测三个核心命题上已经超过常见开源 demo，但作为一个「Agent 平台」还有四类结构性缺口：

1. **可观测性是私有格式**。agent_events 与 tool_executions 事件溯源非常完整，但没有对齐 OpenTelemetry GenAI 语义约定，导不出去也接不进 Langfuse / Jaeger 等标准工具。这与「可评测」的命题直接相关，是本轮性价比最高的补充。
2. **闭环缺最后一公里：线上坏例没有自动回流路径**。L1/L2 评测与证据包都在，但一条真实失败会话变成回归用例仍是手工过程。业界已把「trace 转 test」当作评测闭环的标准动作。
3. **治理只守输入侧，输出侧没有确定性防线**。注入三分法、能力门控、幂等三道防线都在输入与执行路径上，而回复内容的金额与政策引用仍靠提示词自律，没有可断言的 groundedness 检查。
4. **常用工程功能缺口集中在运维面**：限流、请求超时、会话生命周期、附件上传、站外通知、API 文档、指标暴露。多数是 LIMITATIONS 已经自己点名的项，成本低、收益直接。

不建议做的方向：MCP/A2A 全量接入、通用工作流平台、多租户、多语言。理由见末节。

## 调研方法与证据边界

- 本地证据来自当前工作树源码直接读取，每项给出文件定位；「已有」指源码存在，不代表本轮重新运行验证。
- 外部证据分两档：直接读取并核对的官方规范页（OpenTelemetry GenAI 语义约定原文）；搜索摘要级证据（厂商产品页、官方文档主题、社区文章），后者只用于判断业界共识方向，不用于支撑具体数字。
- 本轮没有 build、没有运行付费模型、没有修改业务源码、没有重跑测试。
- 「建议」是基于项目定位（可评测可恢复的售后 Agent 平台，离线优先）的工程判断，不是市场调研结论。

## Agent 方向差距与建议

### A1 标准化可观测性导出（P0，成本中）

**差距**。事件数据非常全（模型轮次、工具参数、延迟、错误码、token 用量、压缩事件），但全部是私有事件格式，只在自家页面消费。OTel GenAI 语义约定已经把 Agent 系统的标准信号定义清楚，当前为 Development 状态但仍是最广泛的跨工具公约。

**业界现状**。规范定义了这些 span（[GenAI Spans 原文](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)，本轮已读取）：

- `gen_ai.inference.client`：模型调用，含 `gen_ai.conversation.id`、`gen_ai.prompt.name/version`、`gen_ai.usage.input_tokens/output_tokens`、`gen_ai.response.time_to_first_chunk`、`gen_ai.conversation.compacted`
- `execute_tool`：工具执行 span
- 另有 embeddings、retrievals、**memory**、fetch response 等 span 类型

对本项目最有意思的一点：规范专门有「compacted conversation」属性（压缩后的上下文是否生效），而本项目恰好有 `context.compacted` 事件——两者天然对应。业界共识（搜索摘要级）是 2026 年生产 Agent 栈以 OTel + Langfuse/LangSmith 作为可观测标配。

**建议**。不需要引入外部 collector，先做「导出适配层」：

- 把 agent_events + tool_executions + P7 账本映射为符合上述约定的 OTLP JSON trace（一个 run 一个 trace，模型轮次与工具执行为 span）
- 提供 `pnpm trace:export --run <id>` 输出文件，写一个离线校验器断言属性齐全（token、延迟、错误码、conversation id）
- 验收：同一 run 的事件表导出后，span 数量、父子关系、usage 数值与账本一致；不声称已接入任何外部平台

这项与 0928 调研「技能级看板」同向但不同层：那是运营指标，这是标准信号。

### A2 坏例自动回流：trace 转评测用例（P0，成本中）

**差距**。LIMITATIONS 自己写了「无在线采样与线上流量回放 评测全部离线」。评测数据集是手工维护的 dataset.json，一条真实失败会话要变成回归用例需要人工转录。

**业界现状**（搜索摘要级）。evals 作为 CI 门禁 + 从生产 trace 生成 test suite 已经是评测闭环的标准动作（如 agent evals traces-to-test-suites 的实践文章）；0928 调研的「坏例到回归用例」P0 建议与此同向。

**建议**。在本项目上这件事比一般项目便宜，因为事件表就是 trace：

- 做一个「会话转用例」工具：输入 run_id，从 agent_events 提取用户消息序列与期望终态，生成 L1 用例草稿（JSON），人工确认后入 dataset
- 关键约束沿用 0928 调研的结论：禁止无审查自动入库，脱敏后人工确认期望行为
- 验收：任选一条历史 run 一键生成用例草稿，字段与现有 L1 schema 完全兼容，直接可跑

### A3 输出侧确定性 guardrail：groundedness 断言（P0-P1，成本中）

**差距**。安全分流（A/B/C 三类）守的是输入侧，幂等与审批守的是执行侧，但**回复内容本身**没有确定性检查。提示词第 4 条要求「用工具返回的数据回答 不编造金额」，这仍是提示词恳求，而项目自己的设计哲学（LIMITATIONS：结构性防盲提交 而非提示词恳求）恰恰反对此类依赖。

**业界现状**（搜索摘要级）。guardrails 在 2026 年的客户服务 Agent 里是输入+输出双侧的：输出侧常见 groundedness 检查（答案必须能溯源到检索结果或工具返回）、金额与承诺类断言。

**建议**。做两层确定性后检，复用现有 guard.blocked 事件模式：

1. **金额断言**：模型最终回复中出现的退款/补偿金额，必须能在本轮工具结果（政策引擎计算值）中找到；找不到则拦截该条回复并走降级路径（要求重答或转人工）
2. **政策引用断言**：回复若出现政策条款名，必须属于本轮 search_policy 命中的条款集合

验收：构造一条模型编造金额的脚本化用例，断言被拦截且事件可回放；同时证明正常回复零误拦。这项是「有据售后」命题在输出侧的补全，演示价值高。

### A4 跨会话客户记忆（P1，成本中）

**差距**。working memory 是单 run 的，客户下次来开新会话，Agent 对该客户的历史售后一无所知（get_order 的 returns 字段是单订单视角）。业界（LangChain long-term memory、langmem 等，搜索摘要级）已把跨会话记忆当作 Agent 栈标配层。

**建议**。最小版本不要做「模型自写记忆库」，而是**查询式记忆**，这更符合本项目哲学：

- 新增只读工具 `get_customer_history`（或在新会话上下文注入客户历史摘要）：该客户过往售后单、终态、退款历史、CSAT，全部来自数据库事实
- 注入时来源可核验（事件/记录 id），模型不得基于历史限制正当诉求（沿用 0928 调研同一条边界）
- 验收：同客户新会话中问「我上次退的那个单子怎么样了」，不要求客户提供订单号即可正确答复且金额准确

与 0928 调研「客户与订单历史视图」部分重叠：那是坐席侧视图，这是 Agent 侧上下文，可以共用同一个读模型。

### A5 技能目录与 Agent Skills 规范格式（P1，成本中，与 0928 调研 P0 同向）

0928 调研已经给出「技能目录与逐项发布」的运营产品建议（每意图绑定工具与版本，草稿测试后发布）。本轮补充一个具体载体建议：Agent Skills 已有开放规范（[agentskills.io](https://agentskills.io/specification)），核心是 SKILL.md（YAML frontmatter + 正文）+ 渐进披露 + 可选脚本，Claude 生态与多家客户端已支持。对本项目：

- 把「退款 / 退货 / 价保 / 补偿 / 物流咨询 / 政策解释」每个业务能力写成一个技能单元（frontmatter 记录绑定工具、版本、风险等级），运行时按会话能力集动态拼装
- 这同时解决「能力门控」的声明化问题：现在工具可见性是代码硬编码，技能化后变成可审计的配置，运营可看
- 验收：同一技能在不同会话快照下工具目录一致；发布新版本后新会话采用、旧会话保持冻结（复用现有快照机制）

注意：本项目根目录的 skills-lock.json 是开发工具技能清单，与运行时技能无关，不要混淆。

### A6 MCP 接口（P1-P2，成本中，谨慎）

**现状**。工具是内部注册表，无任何 MCP 接口。MCP 已成为工具接入的事实标准，官方 Registry 处于 preview（[官方仓库](https://github.com/modelcontextprotocol/registry)，搜索摘要级确认）。

**建议**。对本项目最有价值的不是消费外部工具，而是**暴露**：把只读查询工具（订单、物流、政策检索）经一个 MCP server 暴露，让外部 Agent 客户端（如 Claude Desktop）能查这套模拟售后数据。这验证的是「平台」叙事——工具生态可被外部消费。副作用工具不暴露，边界与现有设计一致。

验收：标准 MCP 客户端列出工具、执行一次只读查询、拿到结果；不接 Registry、不做鉴权体系（演示环境）。

### A7 Judge 校准与在线采样（P1-P2）

LIMITATIONS 已如实记录：Judge 只评主观判据、未校准、评测全离线、模拟器终态不驱动完结轮导致十余条用例悬停。这两个是已知缺口，本轮不展开新建议，只确认它们在业界属于必答题而非加分题（搜索摘要级）。若做，优先修「终态悬停」这个装具缺陷，它污染 L2 分母。

### A8 多 Agent：A2A 与子代理（P2，不建议现在做）

P8 双分支调查已提供并行对照实验，且未接入默认路由——这说明项目对「多 Agent 数量不等于产品价值」已有判断（0928 调研同样结论）。A2A 协议（Linux Foundation 托管，2026-04 宣布生产可用，搜索摘要级）解决的是跨厂商 Agent 互操作，与本项目单租户离线定位距离最远。列入观察，不排期。

## 优先级汇总（两轮调研合并视图）

按「强化核心命题 > 补齐已知短板 > 生态叙事」排序：

1. **A3 输出侧 guardrail + P0 限流/超时 + 会话生命周期**：小到中等成本，全部强化「安全工作」命题
2. **A1 OTel 导出 + A2 trace 转用例**：把「可评测」从离线扩展到可观测、可回流，两件事共享同一份事件表
3. **A4 客户历史上下文 + 附件上传 + 站外通知**：补业务面常用功能，其中客户历史同时是坐席视图的读模型
4. **A5 技能目录（Agent Skills 载体）+ OpenAPI + 指标**：声明化能力管理与平台自描述
5. **A6 MCP 暴露**：平台叙事加分项
6. 观察不排期：A8 多 Agent 协议、多语言、多租户

## 不建议现在做的

- **消费外部 MCP 工具接真实系统**：与离线优先定位冲突，接入成本高且无法离线验收
- **A2A / 通用多 Agent 编排框架**：P8 实验已证明项目对此有清醒判断，重申该结论
- **自研记忆向量库**：A4 用数据库事实查询即可满足，embedding 检索在政策 RAG 试验里已有结论（BM25 与 LLM 精排各有取舍），不要为「记忆」引入第二套检索体系
- **把 OTel 导出做成实时 collector 常驻**：离线导出 + 校验器已满足命题，实时链路是运维负担
- **无审查的自动化坏例入库**：0928 调研同款红线，评测集污染比缺用例更伤

## 仍需确认的信息

- 项目最终目标是求职作品、单商家内部工具还是多商家产品——这决定 P1 认证升级与多租户是否提前
- 真实模型启用后的会话量级——决定限流分级与指标的具体口径
- 是否计划对外演示 MCP 能力——决定 A6 排期

本轮调研没有调用付费模型、没有修改任何业务源码、没有重跑测试，以上「已有」判断均来自源码静态读取，外部规范引用均已标注证据等级。
