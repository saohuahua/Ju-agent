# 渐进重建练习

练习目标是从小闭环理解设计为何需要增加状态、事务和恢复协议。它不是第二套生产项目，也不是要求复制仓库所有功能。参考解法给出关键数据与处理顺序，读者自行实现；遇到错误先保存输入、数据库和日志，不能用清库制造通过。

## 环境与隔离

建议在仓库外建立独立目录，例如 `D:\project\aftersales-learning-lab`；这里只是练习目录建议，本次交付没有创建或运行完整教学工程。运行时可参考现有 Node 22.23.2、TypeScript 和 SQLite 工具链，实际依赖由读者在练习目录单独管理，不修改原项目的锁文件和业务库。

练习使用三条人工构造订单：客户 A 的未发货小额订单、客户 A 的已签收大额订单、客户 B 的订单。金额用整数分，时间作为可注入输入，模型和渠道均用本地可控模拟器。第三条仅用于越权反例，不应被客户 A 成功查询或退款。

每阶段保存一个简短记录：输入和预期、实际观察、失败原因、修改点和证据位置。业务实验目录与代码目录分离。学习者尚未执行的阶段不能标为通过；完整现成项目的复现命令见[演示手册](../runbooks/p11-local-offline-demo.md)。

## 练习一 只有表单的最小退款

对应第 01、04、05 章。先不用模型，输入客户身份、订单号和原因，服务端重新读取订单，决定允许、拒绝或等待批准。实现一个受理接口与一个结果查询接口，使“收到申请”与“完成退款”有不同输出。

最小数据需要订单、申请、退款结果。身份来自服务端认证映射，不能相信请求体里的客户号。保存金额、币种和原订单关系，不只保存一段成功文本。

**验收条件**：A 可以处理自己的有效订单；A 访问 B 的订单被拒绝；请求携带修改后的价格也不能改变实际金额；政策拒绝不产生渠道动作。保存四种输入和返回，并核对数据库中是否真的创建了退款。

**参考解法**：先完成身份和格式校验，再在领域层读取订单、判断状态与计算方案。此时先用无故障模拟渠道观察正常链路，明确这一版尚未解决重复请求和响应丢失。若直接把请求金额转给渠道，失败根因在信任边界，不能用更详细的 Prompt 修复。

源码参考：[after-sale-service.ts](../../packages/domain/src/services/after-sale-service.ts)、[policy.ts](../../packages/domain/src/policy.ts)。

## 练习二 请求去重与业务去重

对应第 06、14 章。给受理接口加入请求键，记录调用者、动作、输入摘要与原结果身份；同键同参返回原结果，同键异参返回冲突。再为一笔退款定义稳定业务键，防止换一个请求键绕过业务去重。

**验收条件**：同一请求重放不会多建申请；同键修改订单会冲突；两个独立连接同时提交同一业务只保留一个胜者；失败时没有只保存了一半的命令。必须同时检查记录数量和返回身份，不能只看两个请求都得到 200。

**参考解法**：唯一约束定义业务身份，事务保证相关记录共同提交，冲突后读取已受理事实。不要仅用“先查没有，再插入”保护并发，也不要把前端禁用按钮作为服务端幂等。此阶段可以有意保留“外部结果未知尚未处理”的限制，下一阶段再解决。

源码参考：[ConversationJournal.accept](../../packages/persistence/src/conversation-journal.ts)、[P6 任务受理](../../packages/persistence/src/p6-task-repository.ts)。

## 练习三 加入受控模型循环

对应第 08–12 章。先使用固定脚本模型，只提供查单、政策查询、补问和申请动作。让模型返回带调用 ID 的结构化意图，宿主验证并执行，把结果回填原调用；不要让模型直接操作数据库或渠道。

**验收条件**：缺少订单时进入补问；用户补充后恢复原调用配对；不存在的工具、参数格式错误、重复调用 ID 和半段参数流不能被当作成功执行；达到轮数上限时有可解释终态；模型声称成功不能改变退款记录。

**参考解法**：模型轮次和工具结果分别保存确认点。完整协议才形成成功轮次，业务校验独立于 Schema。先做到从事件重建消息，不提前引入摘要、向量记忆或复杂框架。只读工具失败与副作用未知应有不同错误类型，便于后面选择恢复动作。

源码参考：[durable-conversation.ts](../../packages/runtime/src/durable-conversation.ts)、[p7-protocol.ts](../../packages/runtime/src/p7-protocol.ts)。

## 练习四 持久任务、审批与抢占

对应第 07、13、15 章。受理只创建持久命令和任务，独立 Worker 领取并推进。增加 owner、generation、leaseUntil 和检查点；审批决定与待执行意图同事务写入。大额订单批准前不得发送资金。

**验收条件**：受理后退出，重启能找到原任务；两个 Worker 竞争只有有效资格者确认；暂停 A 使 B 接管后，A 的迟到结果被拒绝；批准与拒绝竞争只产生一个决定；意图写入失败时决定回滚；租约时间到期不清除退款身份。

**参考解法**：同一写事务内认领并计算配额，每次确认重验代次。外部网络调用不放在数据库事务里等待。审批令牌消费与任务受理共同提交；退货等待与收货任务必须绑定原批准方案，不能建立新退款绕过审批。

源码参考：[P6Worker](../../packages/runtime/src/p6-worker.ts)、[审批原子性实验](../experiments/approval-atomicity.md)。

## 练习五 资金结果未知与投影恢复

对应第 14、16 章。建立独立模拟渠道库，按业务键记录提交与执行。发送前先保存意图；渠道先提交成功，再故意丢弃响应，使业务库暂时不知道真实结果。新进程只能查询原交易并确认。

**验收条件**：正常场景提交 1、动作 1；响应丢失后恢复仍是提交 1、动作 1，查询增加；写意图后但发送前退出时不得通过清记录强行重发；渠道持续未知时业务保持待核验；业务确认后、客户投影前退出，恢复只补原工具结果和完成事件。

**参考解法**：将“允许首次发送”和“已经存在意图”作为不同分支。前者才允许执行，后者核验原业务键。业务结果、任务结束和事件投影分别有可追踪身份。要证明进程恢复，必须结束旧进程并启动新进程，不能在同一个 catch 中重调函数冒充。

源码参考：[客户故障实验](../../apps/api/test/conversation-refund-process.test.ts)、[模拟渠道](../../packages/persistence/src/p6-payment-simulator.ts)。

## 练习六 客户事件与前端重建

对应第 17 章。给持久事件设置稳定运行序号，客户接口使用白名单。实现游标补发和前端按运行、序号去重，身份切换时清理旧连接并隔离普通请求的迟到结果。

**验收条件**：断开再连接只补消息，不新增退款；重复事件不产生重复气泡；隐藏事件不透出 payload，游标仍能前进；切换 A 到 B 后 A 的迟到结果不能覆盖；运行终态事件后仍可收到尾部公开事件，直到传输完成帧再关闭。

**参考解法**：持久表是事件事实源，SSE 是交付通道，前端归约是展示。不要把这三者合并成一个内存数组。请求选择版本需要覆盖离开又回到同一会话的情况，单纯比较 runId 不能区分两次选择。

源码参考：[SSE 服务端](../../apps/api/src/sse.ts)、[CustomerWorkspace](../../apps/web/src/components/customer/CustomerWorkspace.tsx)。

## 练习七 共享预算与失败证据

对应第 18、20 章。模型调用前按上界预占，用整数单位结算，每次尝试有独立记录。构造成功、超时、缺 usage、429 后重试四类输入，再为固定任务保存逐例判定和费用引用。

**验收条件**：两个并发请求不能共同越过限额；重试不覆盖第一笔记录；缺 usage 不记零；重启保留 held／unknown；业务成功但 Judge 失败时两个指标不同；没有样本的类别不能标成质量通过；篡改失败索引会使证据核验失败。

**参考解法**：费用状态与本地协程数分开，取消收尾后仍可能保留并发风险。先用固定模型验证协议，不把模拟价格作为真实账单。将题集、配置、版本及允许变化变量一起保存，比较报告才有可解释前提。

源码参考：[P7Ledger](../../packages/persistence/src/p7-ledger.ts)、[P9 报告](../../packages/eval/src/p9-report.ts)。

## 练习八 双库恢复与可讲述交付

对应第 21、22 章。结束写入者后备份业务库和渠道库，保存哈希清单，恢复到新空目录。对比原运行、退款、任务、事件、费用和渠道计数，再写一页设计说明。

**验收条件**：恢复后成功保持成功、未知保持未知，计数与原关联一致；哈希不符拒绝恢复；非空目标不覆盖；不使用 db:reset 或 down -v 作为正常步骤；演示命令注明目录、数据、身份、停止与恢复方法。

**参考解法**：两次单库 backup 需要共同停写前提。重启原目录、恢复备份到新目录和重新创建一套演示，是三种不同操作。设计说明只需讲清约束、方案、关键记录、正常和异常分支及证据；不要把尚未执行的 Docker 实验写成通过。

源码参考：[双库脚本](../../scripts/p10-data.ts)、[现成演示手册](../runbooks/p11-local-offline-demo.md)。

## 练习记录如何评审

每阶段至少回答：哪条事实必须保存，谁有权写，写入与哪条记录共同提交，退出后依据什么继续，实验怎样排除“看似成功但重复执行”。若这些问题都能用自己的小实现和证据回答，再用[集中自测](集中自测.md)检查概念漏洞。

当前交付提供练习与参考设计，不声称读者已经实现，也没有把完整教学工程留成待填空壳。可运行的原项目演示是独立交付，两者用途不同。
