## 目标读者与表达约定

目标岗位为 Agent 应用／全栈研发。读者熟悉前端，能够独立编写 TypeScript／JavaScript 业务功能；后端知识需要结合项目补齐，Agent 概念尚未串成完整链路。学习目标是读懂当前实现、解释设计与证据，并能参照材料重建精简核心闭环。

正文采用客观叙述的教材式讲解，用具体业务问题引出必要原理，再连接源码、实验和设计取舍。以连贯段落为主，不刻意分点；只有并列信息、操作顺序和核查清单采用列表。首次出现的技术术语需解释，以技术反例纠正误解，少量类比必须说明边界。

整体篇幅大致分配为原理 30%、源码 30%、业务案例与实验 25%、面试内容 15%，不作为逐章硬配额。核心章节通常 3000–5000 字，不含图、代码和证据索引；总量不设硬上限。22 个正文单元预计约 6.6–11 万字，面经和练习另计。标题最多三级，不用篇幅填充代替解释。

学习路线采用单线递进。后端基础以理解和重建本项目为限，解释并发和恢复时深入必要底层机制，不扩成通用 Node 或数据库课程。Agent 正文补齐模型消息、token、工具协议等必要基础；框架、MCP、向量检索等内容先核实采用情况，未采用部分放独立扩展专题，由面经引用，不写成项目实战。

## 面试、贡献与证据

核心面试答案是 60–90 秒的自然专业口语，配 1–2 层递进追问。并发、故障和替代方案由相邻问题或深入章节承载，不压入每道题的首轮回答。面试表达不强制逐题套 STAR，不把所有问题扩成漫长口播。

个人贡献待核实。简历材料先列项目已实现能力、验证条件、可追溯数字、尚未验证内容与归属待确认项，不将源码存在等同于本人独立实现。用户当前已明确不因贡献核实而阻塞学习文档。

计划说明预期，源码说明实现，实验说明在哪个版本和条件下验证。三者冲突时核查并在相应结论处说明。历史真实模型成绩不用于证明当前版本质量，单元集成测试与 L1 不混算，P8 模块能力不自动等同于默认客户入口能力。P10 尚未完成的容器验收不阻塞写作，也不能因写作而标成完成。

## 样章与验收方式

### 样章反馈后的额外写作要求

2026-09-27 用户补充：学习和面试最关注“如何实现、实现思路是什么”。此要求优先于机械执行原篇幅比例，保留原理解释，但以设计推导和实现过程为核心。

- **实现思路前置。** 简短业务引入后，先说明要保证什么、困难或约束在哪里、为什么简单方案不够，再说明关键设计与模块协作。必要时使用核心代码与 SVG，代码不成为主体。
- **思路具体到核心协作。** 说明关键记录各保存什么、哪些写入共同提交、执行器依据什么选择分支，以及结果怎样交给后续模块。只展开支撑设计的核心处理，不逐函数罗列实现。
- **实现思路完整但不堆细节。** 后续核心章节至少交代目标与约束、最小可行方案、关键设计决定、模块输入输出与协作、正常流程及最重要的异常分支。读者应能据此解释或勾画一个最小实现，不必依赖遍读源码才能知道方案怎么设计。
- **按需要展示从小到大的推导。** 可从最小方案出发，指出它在具体条件下的缺口，再解释为什么增加状态、持久化、权限或协调机制。每次增加复杂度都要对应一个真实问题，不为讲故事虚构早期版本、失败经历或个人贡献。有记录支持的才称历史演进；为教学构造的递进方案明确称设计推导，尚未实现的补强明确称扩展方案。
- **阅读前提简短明确。** 章首列出必需基础与建议先读的章节，控制在核心依赖内。样章阶段如前置章节未交付，应标明规划状态，不创建无效链接。全书完成后换为真实章节链接。
- **不设置章首实现范围。** 删除固定“实现范围”块。必要的模拟条件、历史日期和验证限制放在对应案例、验证依据或设计取舍处，不重复占用开头。
- **突出设计依据。** 不仅说明做了哪些步骤，还要解释为什么使用这样的业务身份、状态、事务边界和恢复路径。亮点由具体问题、机制和验证体现，不使用宣传性评价。
- **正文压缩去重。** 思路部分已经交代的流程，后文不再完整复述；正文集中补充必要原理、实现细节、异常案例与证据。3000–5000 字是通常阅读单元，不为满足字数补充重复内容。
- **明确主次。** 关键结论、前提和转折适量加粗；执行顺序用有序列表，并列条件、责任和取舍用无序列表。长句包含多个独立判断时适当拆分，不把每句话都改成列表。
- **使用直接标题。** 使用“实现思路”“源码参考”“验证依据”“设计取舍”等标题，删除“沿源码验证，而不是只背结论”等引导或说教式过渡，不在教材中反复评价读者应该如何学习。
- **颜色只作辅助。** 使用 Markdown 加粗、引用块、列表和图示建立主要层级。SVG 颜色配合文字表达意义；正文不依赖固定字体颜色传达关键内容，避免 Typora 主题变化后失去可读性。

### 确认与检查

已确认样章为 [第 14 章 退款幂等与结果未知](../05-资金执行与恢复/14-退款幂等与结果未知.md)。2026-09-27 用户接受当前样章，要求后续实现思路更完整，并同步规范。后续沿 22 章路线编写，不重复进行写作偏好访谈，也不逐章征求许可；若用户提出新要求，更新本文并同步入口摘要。

续写前先读本约定、样章和当前章节涉及的真实源码与证据。完成一章后检查：只读实现思路能否讲清设计理由与核心流程；后文是否主要提供必要细节而非重复前文；前置章节是否真实存在；未采用方案和教学推导是否与已实现事实区分。纯业务、导航或复现章节按其用途组织，不为统一外观虚构技术实现。

交付前检查链接、命令、术语、数字与图文控制流，核心结论须指向真实实现与适用证据。检查是否存在承诺未交付的章节、空壳和未标注的过时描述。新增验证只用于解决具体不确定性，不默认 build，不无变化重复全仓检查，不调用真实模型或真实资金，不修改业务实现，不提交或推送 Git。

Typora 的实际显示与 SVG／Mermaid 语法检查分别记录，未在目标载体直接验证的项目不宣称通过。新增示例代码若包含注释，使用精炼中文且不加标点符号。
