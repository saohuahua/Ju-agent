# 业务流程练习解析

本解析对应[业务流程练习](业务流程练习.md)，用于核对判断链。它说明题目能从教材得到哪些依据，不证明读者已经掌握，也不表示本次执行了测试或资金演示。

## B01 能力边界

**B01A**：结论不成立。需核实客户工具是否开放、执行时是否允许该动作、原方案能否持久受理、授权与结果能否关联原会话。业务 Worker 支持已有补偿任务不等于客户已能创建该任务。见[B01](../03-业务逻辑详解/B01-业务能力全景与角色分工.md)、[B08](../03-业务逻辑详解/B08-补偿价保与换货.md)。

**B01B**：查询本人候选，客户确认订单及具体商品，保留原故障诉求，明确办理类型，再提交结构化意图。Agent 取证和补问，领域服务重查归属、重复申请与资格金额。候选不能代替用户选择，多商品不能默认整单退货。依据为 B01 与现有订单选择测试。

## B02 状态职责

**B02A**：不矛盾。等待任务已经完成授权等待的执行片段，售后仍等客户寄回，退款只是预留。后续客户登记后变 buyer_shipped，操作员确认收货后受理原退款，渠道明确成功再完成业务。见[B02](../03-业务逻辑详解/B02-业务对象与状态关系.md)。

**B02B**：查原任务是否 needs_confirmation、资金效果是否明确、执行权是否 sending 或 unknown，并核对售后与退款成功事实是否一致。状态表允许迁移只是必要条件；执行权及原渠道事实仍可阻止发送。不能根据退款表没有 unknown 就认定不存在资金未知。

## B03 规则推导

**B03A**：4999.99 元允许自动处理，5000 元需审批；质量问题仅退款 20 元仍需审批，原因规则先要求人工确认。输入已假定无其他限制，仍不能把 allow 等同于资金成功。见[B03](../03-业务逻辑详解/B03-售后资格与金额如何判定.md)。

**B03B**：恰好七天允许，多一毫秒拒绝；规则按精确时间差。混合订单包含生鲜时，当前 R4 检查整单而非选中商品，所以仍拒绝。不要以自然日或商品金额范围替代资格范围。

**B03C**：整单 32000 分，只选 A 为 24000 分。itemIds 选择商品行，没有单独的退货数量参数；订单级重复限制也不能支持“首次退完再随意退剩余”。本项目没有完整逐件余额账本。

**B03D**：合法申请被政策拒绝会保存 rejected 售后，不预留退款；越权在受理检查时拒绝，不能给他人订单建单。售后金额函数只筛选命中项，价保服务显式逐个核验商品归属，不能宣称两者同等严格。见 B03 的输入边界说明。

## B04 受理与资金

**B04A**：API 保存输入命令和任务后返回 202；Worker 补问并取得可信订单；模型提出仅退款意图；受理事务重查事实并保存售后、退款、执行权、原调用和授权任务；资金 Worker 执行原方案；明确结算后补原工具结果及客户事件。可信身份来自认证和原任务，金额来自订单规则。见[B04](../03-业务逻辑详解/B04-仅退款的完整业务实现.md)。

**B04B**：HTTP 响应丢失时同键同内容定位原命令，换新键并不消除业务重复检查。渠道响应丢失时要按原业务键查结果，保留发送许可，不得重新建单或换键发钱。前者恢复一次输入的受理结果，后者核实外部资金事实。

## B05 寄回与收货

**B05A**：不应成功。原授权先合法受理，再由客户登记寄回，售后进入 buyer_shipped，操作员才可核对原授权并受理收货任务。这里不要求等待任务必须显示 completed，其可衔接状态以原授权协议为准。批准证明允许继续，登记证明接受寄回信息，收货证明允许收货后处理，资金确认才证明退款成功。见[B05](../03-业务逻辑详解/B05-退货后退款的完整业务实现.md)。

**B05B**：原请求重放找回同一命令，buyer_shipped 分支不重复推进；不同运单再次提交不等于具备修改功能。人工接管后，客户消息入口拒绝结构化寄回，但普通留言仍允许。前端必须分别解释“留言保存”和“寄回登记”。

## B06 决定与授权

**B06A**：数据库在 pending、有效期、运行和检查点条件仍匹配时更新，只有有效更新的决定生效。失败方重读分类。决定与执行意图共同提交，重启后扫描 pending 意图继续受理；不是依赖原 API 进程的内存回调。见[B06](../03-业务逻辑详解/B06-自动处理与人工审批.md)。

**B06B**：不能。时限不能抹去已经可能发送的资金，未知执行权仍阻止重新授权。自动批准依据领域允许结果及原命令，不创建不存在的人工令牌，但仍经过持久受理和资金保护。

## B07 案件范围

**B07A**：退款 executing 不在允许结案白名单，仍阻塞。预览不是授权，提交时事务内重新核验，新补偿未执行会导致结案失败。只有通过后，运行完成、客户事件和审计才共同写入。见[B07](../03-业务逻辑详解/B07-人工接管与结案.md)。

**B07B**：不能证明。当前核验按本运行的审计、审批、检查点和任务查关联，不沿 human.requested.sourceRunId 递归核验。B 是关联沟通案件，A 仍保留资金业务。跨案件统一结案属于待设计能力，不可冒称已实现。

## B08 不同业务

**B08A**：50 元自动，50.01 元审批；failed 补偿仍占同订单同原因位置，不能新建单绕过。后续只能依据原业务的安全处理条件推进。见[B08](../03-业务逻辑详解/B08-补偿价保与换货.md)。

**B08B**：整单差价为 `(100−80)×2=40` 元，B 涨价不参与；只选 B 则拒赔。已有 failed 售后会触发价保活跃售后限制；缺少 A 当前价时不虚构降价，只有 B 又无降价则拒赔。

**B08C**：不能。准确表述为已有换货售后分支，支持寄回与收货后的完结留痕，不创建退款；未证明库存扣减、补发订单与新物流履约。不能把行业应有流程当作代码事实。

## B09 事实与体验

**B09A**：当前 API 对持久会话主动物流注入返回冲突，不能据旧服务能力推断当前可用。物流服务更新运单，没有据此证明订单 deliveredAt 同步更新，窗口判断仍读取订单签收时间。见[B09](../03-业务逻辑详解/B09-物流事实与服务评价.md)。

**B09B**：满足本人会话、一 run 一评、合法分数等条件时可以评价；不会推进资金或会话状态。customer 是来源口径，不证明真实商业用户；completed 还包含咨询和人工结束，不能充当自动退款成功率。

## B10 页面与精简实现

**B10A**：依服务端客户进度的完整事实判断，部分成功不一致会保守待核验，未知优先于人工状态。SSE 断线不结束后台任务，重连后补事件并查询快照。见[B10](../03-业务逻辑详解/B10-从业务事实到客户页面.md)。

**B10B**：参考设计应包含下面这些职责，但具体实现可简化技术框架。

| 动作 | 身份及输入 | 必要核验 | 记录变化 | 完成判据 |
| --- | --- | --- | --- | --- |
| 申请 | 本人订单、类型、原因、商品范围 | 归属、重复、资格、金额、审批 | 售后、可选退款、授权及待办 | 方案被可靠受理，不等于退款 |
| 寄回 | 原客户、原售后、运单 | 原关联、待寄回、类型 | buyer_shipped 和审计 | 登记成立，等仓库 |
| 收货 | 操作员、原售后 | 已寄回、原授权、未发送执行条件 | 原收货任务和关联 | 后续任务受理 |
| 资金及反馈 | 原方案和渠道结果 | 身份金额一致、原发送许可、结果确认 | 退款、售后、资金效果及客户事件 | 明确结果，未知保留核验 |

加入 Agent 后替换或增强的是诉求收集、查询顺序和补问，身份、金额、资格、授权、状态迁移与资金确认仍由服务端控制。若你的设计只有一个任意改 status 的接口，或把业务等待保存在组件内存里，应回到 B02、B05 重画。

## 题目反向覆盖复核

本次先依据题目给定事实和已读取源码写出参考判断，再逐题检查正文是否包含对应推导依据。B01—B10 共 23 题都有正文落点；跨案件结案、部分商品校验和评价开放状态均保留实际限制，没有用理想实现填补答案。

这是一轮教材覆盖度自查，没有进行真实读者盲测，也未据此给学习效果评分。建议读者保存首次答案，重读后只重做缺失判断链的题目。
