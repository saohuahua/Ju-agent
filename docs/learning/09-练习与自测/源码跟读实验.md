# 源码跟读实验

这组练习和[渐进重建练习](渐进重建练习.md)分工不同：**本篇只做"读懂现有代码"的观察，不要求你从零搭一个子系统。** 每个实验 10–20 分钟可以开始并完成一次明确观察，用来确认你真的定位到了行为，而不是记住了结论。

> **三条安全边界**
> 1. **默认路径全部只用读代码完成**，不启动服务、不连数据库、不调用模型。
> 2. 只有实验 7 提供一条可选命令，它会**写出本地报告产物**；不需要它也能完成实验。
> 3. **不要运行 `pnpm db:reset`（会清空数据）**，也不要为了观察而删除 `data/` 目录或容器卷。

建议在编辑器里打开"要看的文件"，对照本页的步骤逐个确认，并把观察记在一张表里：**事实 → 来自哪个文件哪一行 → 我的结论**。记录的价值大于结论本身。

## 实验 1 跟踪一次 HTTP 受理，区分 202 与业务完成

**学习目标**：分清"输入已受理"和"退款已完成"，并知道这个区分在代码里的位置。

**开始前需要知道**：Hono 的路由注册方式、异步函数、HTTP 状态码的含义。

**要打开的文件与函数**

| 文件 | 看什么 |
| --- | --- |
| [`apps/api/src/app.ts`](../../../apps/api/src/app.ts) | `app.post('/api/runs'`，以及 `if (system.conversations)` 分支 |
| [`apps/api/src/model-entry.ts`](../../../apps/api/src/model-entry.ts) | `resolveApiModelEntry` |
| [`packages/persistence/src/conversation-journal.ts`](../../../packages/persistence/src/conversation-journal.ts) | `accept` |

**跟读步骤**

1. 在 `app.ts` 里找到 `app.post('/api/runs'`，先确认它进入持久分支的条件。
2. 读持久分支的 `return` 语句：记下状态码和响应体的四个字段名。
3. 继续往下读十几行，找到没有持久会话时走的那条兼容分支，比较它的状态码和字段。
4. 打开 `model-entry.ts`，确认什么条件下才会装配 `durableConversation`。
5. 打开 `conversation-journal.ts` 的 `accept`，列出它在同一个事务里写入的**表名**。

**关键观察点**

- 202 的响应体里只有标识，没有任何业务结论字段。
- 同一个事务里写的是命令、任务和运行事件——**没有售后单，也没有退款单**。
- 装配生产 `system.conversations` 的开关来自环境变量，而不是源码里的常量。

**验收问题**：页面收到 202 后立刻显示"退款处理中"，这个"处理中"的依据应该来自哪里？如果来自这次响应的字段，会错在哪？

**常见误解**：把 202 当成"退款成功回执"；以为不设环境变量时也走持久路径（那样会看到 201）。

**深入**：[第 02 章](../01-项目全貌/02-一次退款请求的全景.md)、[第 04 章](../02-后端必要基础/04-HTTP接口与身份边界.md)、[第 07 章](../02-后端必要基础/07-状态机与异步任务.md)

## 实验 2 找到模型 Tool Call 的完整链路

**学习目标**：从模型流式输出一路追到宿主执行工具，并指出所有"拒绝半成品"的位置。

**开始前需要知道**：`AsyncIterable`、JSON 解析、什么是流式响应。

**要打开的文件与函数**

| 文件 | 看什么 |
| --- | --- |
| [`packages/agent/src/model.ts`](../../../packages/agent/src/model.ts) | `ModelStreamEvent` 的四类事件 |
| [`packages/runtime/src/durable-conversation.ts`](../../../packages/runtime/src/durable-conversation.ts) | `collect`、`execute` |
| [`packages/runtime/src/p7-protocol.ts`](../../../packages/runtime/src/p7-protocol.ts) | `decodeP7Stream`、`validateP7Request` |

**跟读步骤**

1. 在 `model.ts` 里抄下四类流事件的名称与字段（注意参数增量事件的精确拼写）。
2. 在 `durable-conversation.ts` 找 `collect`，看文本和参数分别怎么累积。
3. 找到它拒绝不完整轮次的两处判断，记下抛出的错误文本。
4. 回到 `execute` 的主循环，找到"工具执行之前"的检查点判断。
5. 在 `p7-protocol.ts` 里找出判定"一轮完整"的依据，以及哪些情况会判协议错误。

**关键观察点**

- **参数按 `toolCallId` 累积在内存里，只有拿到完成标记才解析。**
- 拒绝半成品的位置不止一处：协议层一轮完整性、轮次截断、会话层跨轮 ID 复用。
- 工具目录是在进入循环**之前**确定的，不是每轮按查询结果动态变化。

**验收问题**：假设模型输出了一半参数就断线，请按顺序说出有哪几处会阻止它被执行。

**常见误解**：以为"页面已经显示了一部分文字"就代表模型轮次已经确认。

**深入**：[第 09 章](../04-Agent机制/09-原生工具调用与Agent循环.md)

## 实验 3 观察一次 Tool Call ID 与 Tool Result 的配对

**学习目标**：理解为什么工具结果不能当普通文本塞回上下文。

**开始前需要知道**：消息角色（`user` / `assistant`）的概念，知道工具结果是宿主产生的。

**要打开的文件与函数**

| 文件 | 看什么 |
| --- | --- |
| [`packages/agent/src/context.ts`](../../../packages/agent/src/context.ts) | `rebuildMessages`，以及 `unansweredCalls`、`seenCalls` |
| [`packages/persistence/src/conversation-journal.ts`](../../../packages/persistence/src/conversation-journal.ts) | `append`、`events` |

**跟读步骤**

1. 在 `context.ts` 找 `rebuildMessages`，记下它接收的是**事件行**而不是消息。
2. 找到两个集合的声明，分别想清楚它们各自在防什么。
3. 找到处理 `agent.tool_results` 的分支，看它怎么用 `toolCallId` 配对。
4. 找到处理 `message.user` 里 `replyToToolCallId` 的分支——客户对补问的回复也被合成了一条工具结果。
5. 回到 `conversation-journal.ts`，确认事件是按什么顺序读出来的。

**关键观察点**

- 配对靠**调用标识**，不靠工具名。两个同名工具的结果不会混淆。
- 悬空的工具调用会被补一条合成结果，否则原生协议会拒绝整个请求。
- 消息历史是从**事件表**重建的，不是内存里攒的数组。

**验收问题**：如果某次工具结果事件丢了，重建出来的消息序列会出现什么问题？为什么不能靠"猜一个最近的调用"来补？

**常见误解**：以为数据库里存了聊天记录就等于模型能看到完整上下文。

**深入**：[第 09 章](../04-Agent机制/09-原生工具调用与Agent循环.md)、[第 10 章](../04-Agent机制/10-多轮澄清与上下文管理.md)

## 实验 4 退款领域方案如何决定金额、审批或等待

**学习目标**：证明退款金额来自领域规则，并说清三条分支的触发条件。

**开始前需要知道**：什么是领域服务，什么是纯函数式的方案生成。

**要打开的文件与函数**

| 文件 | 看什么 |
| --- | --- |
| [`packages/persistence/src/p6-conversation-refund.ts`](../../../packages/persistence/src/p6-conversation-refund.ts) | `submit` 的字段白名单 |
| [`packages/domain/src/services/after-sale-service.ts`](../../../packages/domain/src/services/after-sale-service.ts) | `prepareReturnRequest` |
| [`packages/domain/src/policy.ts`](../../../packages/domain/src/policy.ts) | `evaluatePolicy`、`decidePolicy` |

**跟读步骤**

1. 在 `submit` 里找到拒绝非法字段的那段判断，列出它允许的字段清单。
2. 在 `after-sale-service.ts` 找 `prepareReturnRequest`，按顺序找出归属检查和两种重复申请检查。
3. 找到调用政策判定的那一行，确认金额、结果与规则编号都来自这次判定。
4. 找到决定售后单初始状态的三支判断，写出每个分支对应的状态名。
5. 找到创建退款单的条件，确认什么情况下**不会**创建退款单，以及业务键是怎么生成的。

**关键观察点**

- 金额只有一个来源：政策判定。模型参数里根本没有这个字段。
- 归属、重复、政策是三次不同性质的判断，失败信息也不同。
- 退货类型在政策通过后会直接进入等待寄回，仅退款不会。
- 退款单创建时 `status: 'created'` 只是"预留了一个资金身份"，不是钱已发出。

**验收问题**：如果模型在工具参数里加了 `amountCents: 1`，会发生什么？这个错误会在哪一层被拦住？

**常见误解**：把 `refundNo` 当成本地退款完成的标志；以为"自动批准"就等于自动付款。

**深入**：[B03](../03-业务逻辑详解/B03-售后资格与金额如何判定.md)、[B04](../03-业务逻辑详解/B04-仅退款的完整业务实现.md)、[B06](../03-业务逻辑详解/B06-自动处理与人工审批.md)

## 实验 5 两个"防重复"分别防什么

**学习目标**：区分请求级、调度级和业务级三种去重粒度。

**开始前需要知道**：唯一约束、事务、哈希指纹的作用。

**要打开的文件与函数**

| 文件 | 看什么 |
| --- | --- |
| [`packages/contracts/src/idempotency.ts`](../../../packages/contracts/src/idempotency.ts) | `refundIdempotencyKey` |
| [`packages/persistence/src/conversation-journal.ts`](../../../packages/persistence/src/conversation-journal.ts) | `accept` 里的重放比对 |
| [`packages/persistence/src/p6-task-repository.ts`](../../../packages/persistence/src/p6-task-repository.ts) | `accept` 里的指纹比对 |
| [`packages/domain/src/services/after-sale-service.ts`](../../../packages/domain/src/services/after-sale-service.ts) | `prepareReturnRequest` 的重复售后检查 |

**跟读步骤**

1. 读 `idempotency.ts`，写出退款业务键的生成规则。
2. 在 `conversation-journal.ts` 找"已有相同请求键"的处理：它比较的是什么？不一致时报什么错？
3. 在 `p6-task-repository.ts` 找第二次比对：它用的是哪种哈希？比较的字段有哪些？
4. 在 `prepareReturnRequest` 找"同订单已有进行中售后"和"已有已完成售后"两处拒绝。
5. 自己画一张表：**哪一层 → 用什么身份 → 防住哪一种重复**。

**关键观察点**

- 请求键保护**一次 HTTP 输入**，业务键保护**一笔退款**，两者不能互相替代。
- 即使请求键全新，业务层的重复售后检查仍然会拦下第二次申请。
- 资金效果表上也有一层按业务键的指纹校验，防止同键不同金额。

**验收问题**：客户换一个请求键、用同样的订单再申请一次退款，会被哪几层依次拦下？如果只保留最外层会怎样？

**常见误解**：以为前端禁用按钮或请求键就足以防止重复退款。

**深入**：[第 06 章](../02-后端必要基础/06-事务唯一约束与条件更新.md)、[第 14 章](../05-资金执行与恢复/14-退款幂等与结果未知.md)

## 实验 6 结果未知时，恢复为什么是查询而不是重发

**学习目标**：说清"发送意图"和"渠道结果"是两个不同事实，并找出决定查询还是发送的那一行代码。

**开始前需要知道**：事务提交与回滚、外部调用不在事务内。

**要打开的文件与函数**

| 文件 | 看什么 |
| --- | --- |
| [`packages/runtime/src/p6-worker.ts`](../../../packages/runtime/src/p6-worker.ts) | `execute` 里的 `shouldSend` 分支与未知结果处理 |
| [`packages/persistence/src/p6-task-repository.ts`](../../../packages/persistence/src/p6-task-repository.ts) | `effect`、`beginPayment`、`settle` |
| [`packages/persistence/src/p6-payment-simulator.ts`](../../../packages/persistence/src/p6-payment-simulator.ts) | `submissions` 与 `charges` |

**跟读步骤**

1. 在 `p6-worker.ts` 找 Worker 第一次读取资金效果的位置，记下它读的是哪张表。
2. 找到拿到"首次发送许可"的那一行，确认这个许可的返回值直接决定了接下来做什么。
3. 跟着分支看两条路径：一条调用渠道执行，另一条按原业务键查询。
4. 打开 `settle`，找出"已有终态直接返回"和"未找到归一成未知"这两处判断。
5. 回到 Worker，找未知结果把任务置成哪个状态。
6. 在模拟渠道里确认两个计数列各自在什么情况下增加。

**关键观察点**

- **`beginPayment` 的返回值就是"这是不是第一次发送"**，而不是"业务是否批准"。
- 已有意图时即使没有成功记录，也不会重新发送。
- 渠道查询返回的"未找到"被归一成存储态"未知"，因此资金效果表里不会留下"未找到"这个值。
- 提交次数与成功扣款次数是两个独立计数，**只有它们分开才能区分"重发了"和"重复扣款了"**。

**验收问题**：如果一次恢复查询返回"未找到"，系统允许重发吗？这个保守选择让系统失去了什么能力？

**常见误解**：以为"本地没有成功记录"就能推出"钱没退"；以为租约到期会释放资金发送许可。

**深入**：[第 14 章](../05-资金执行与恢复/14-退款幂等与结果未知.md)、[第 15 章](../05-资金执行与恢复/15-Worker租约与检查点.md)、[第 16 章](../05-资金执行与恢复/16-跨进程恢复与人工核验.md)

## 实验 7 在 L1 里定位一条用例的输入、断言、结果和失败原因

**学习目标**：能独立读懂一条评测用例"给了什么、断言什么、为什么判通过或失败"。

**开始前需要知道**：前面的实验 1–6 至少完成三个，否则断言里的业务名词会看不懂。

**要打开的文件与函数**

| 文件 | 看什么 |
| --- | --- |
| [`packages/eval/src/cases/`](../../../packages/eval/src/cases) | 用例数据，建议从 `recovery.ts` 或 `fault-injection.ts` 里挑一条 |
| [`packages/eval/src/cases.ts`](../../../packages/eval/src/cases.ts) | 分类如何聚合、脚本模型如何按顺序消耗 |
| [`packages/eval/src/runner.ts`](../../../packages/eval/src/runner.ts) | 运行一条用例、收集断言 |
| [`packages/eval/src/validators.ts`](../../../packages/eval/src/validators.ts) | 各类断言的具体实现 |
| [`packages/eval/src/p9-report.ts`](../../../packages/eval/src/p9-report.ts) | `failureClasses` 失败分类 |

**跟读步骤（只读路径，推荐）**

1. 在 `cases/` 里挑一条用例，抄下它的 `id`、`category`、`priority`。
2. 读它的 `turns`（用户回合）与 `modelScript`（脚本模型动作），说清这条用例想复现什么场景。
3. 读它的 `assertions`：分出哪些是业务终态、哪些是轨迹、哪些是交互。
4. 在 `runner.ts` 找 `collectAssertions`，看这些断言被转成哪几个失败类型。
5. 在 `p9-report.ts` 找失败分类函数，确认一条失败可能同时命中多类。

**可选命令（会写出本地报告产物）**

```bash
pnpm eval -- --case <用例 id>
```

这条命令来自根 `package.json`，运行离线评测的单个用例，**会生成本地报告文件**。不运行也能完成本实验。**不要运行 `pnpm db:reset`。**

**关键观察点**

- 用例的"成功"由断言定义，不由最终那句回复定义。
- 脚本模型的动作是按顺序消耗的，所以"模型说了什么"在 L1 里是**输入**，不是被测对象。
- 失败分类是**多选**的，计数不能相加当作独立失败用例数。
- `regression` 分类目录为空时贡献 0 条，不改变 124 条基数。

**验收问题**：一条用例只要最终回复是一句正确答案就判通过，会漏掉哪些错误？

**常见误解**：把 L1 通过率当成模型准确率；把失败分类计数相加当成用例总数。

**深入**：[第 20 章](../07-验证与设计取舍/20-测试L1L2与Judge.md)

## 完成标准与记录模板

做完一遍后，你应该能不看本页回答：

1. 一次请求从 HTTP 到资金确认，中间有哪些"确认点"，各自在哪张表？
2. 哪些地方在阻止"半个参数"或"半个结果"被当成既成事实？
3. 防止重复的三层身份分别是什么？
4. 未知结果时，代码依据哪一条记录决定查询而不发送？

记录建议用四列，方便复查与面试引用：

| 列 | 内容 |
| --- | --- |
| 观察 | 我看到的行为，一句话 |
| 出处 | 文件路径 + 函数或方法名 |
| 结论 | 这个行为说明了什么设计决定 |
| 边界 | 它不能证明什么 |
