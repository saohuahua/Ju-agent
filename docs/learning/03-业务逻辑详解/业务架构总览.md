# 业务架构总览

客户的一句售后诉求，需要先转成可信的业务方案，再由有权限的角色和后台执行器共同推进。本图把 **谁参与、依据什么判断、怎样办理、何时算完成** 放在同一张地图里。

> **阅读前提**：本图描述当前仓库的业务分层，不是部署拓扑，也不是严格执行时序。订单与资金渠道仍为模拟；接入真实模型不等于接入真实支付。

![有据售后业务架构图](业务架构图.svg)

图 B00-1 从上到下展示责任层次。箭头表示层间交接，**不表示所有申请都必须依次经过所有方框**。例如政策拒绝不会进入资金发送，物流查询和评分也不必先创建退款。黄色标明条件分支或入口边界。

## 怎样读这张图

1. **先看角色**：客户提供诉求和信息，Agent 查询补问并提出动作，主管作审批决定，操作员补充收货事实或接管沟通。
2. **再看方案**：服务端校验身份和订单归属，依据订单、物流与政策确定类型、金额和是否需审批；后续都围绕原方案继续。
3. **沿业务主线看等待点**：仅退款在有效授权后进入执行；退货退款还要等待客户寄回和操作员收货。批准、寄回、收货各自证明不同事实。
4. **最后看完成依据**：后台依据原业务记录发送或查询，客户页面读取经核验的进度；人工结案另行核验本案关联资源。

### 两条主线怎样走

| 主线 | 正常推进顺序 | 容易误判的地方 | 详细章节 |
| --- | --- | --- | --- |
| 仅退款 | 诉求与事实 → 资格和金额 → 原售后与退款 → 自动授权或主管批准 → 原退款执行 → 结果反馈 | HTTP 202、审批批准都不证明资金成功 | [B04](B04-仅退款的完整业务实现.md)、[B06](B06-自动处理与人工审批.md) |
| 退货后退款 | 诉求与事实 → 原方案和授权 → 客户登记寄回 → 操作员确认收货 → 原退款执行 → 结果反馈 | 等待任务完成不等于退货完成，收货不产生新退款 | [B05](B05-退货后退款的完整业务实现.md) |

这里展示正常主线；政策拒绝、主管拒绝、安全过期和资金待核验都可能阻止继续。对应条件应回到章节规则和当前源码核对。

## 业务对象如何支撑这些交接

- **订单与物流**提供资格判断依据，客户描述不能直接覆盖它们。
- **售后与退款**分别保存申请方案和资金业务，退款记录存在不代表已付款。
- **审批与执行意图**保存原方案的决定及后续待办，批准后仍需可靠交接。
- **命令、任务、执行权与资金效果**保存推进过程，区分当前谁在处理、是否允许发送、渠道结果是否明确。
- **会话、事件与客户进度**组织沟通和展示，不能反过来替代资金事实。

对象之间通过稳定标识关联，关系详见 [B02](B02-业务对象与状态关系.md)。图中省略了具体表结构与事务边界，资金恢复机制见[第 14 章](../05-资金执行与恢复/14-退款幂等与结果未知.md)。

## 横向能力与入口边界

| 能力 | 在架构中的作用 | 当前不能据此推导的能力 |
| --- | --- | --- |
| 物流查询与事件 | 提供配送事实，辅助规则判断 | 持久客户会话已开放主动物流注入，或自动确认退货收货 |
| 人工求助与结案 | 转移沟通责任，核验本案资源后收口 | 新关联人工案件结案就证明来源退款成功 |
| 服务评价与统计 | 保存客户感受，按既定口径统计 | 五星、会话完成率等于资金成功率 |
| 补偿与价保 | 已有独立规则、实体、服务及兼容执行能力 | 默认客户持久入口已经完整接入 |
| 换货 | 复用售后类型及寄回收货流程 | 已实现库存锁定、重新发货与新包裹签收 |

> **人工案件的特别边界**：请求人工可能另开关联会话。当前结案仓储不沿 `sourceRunId` 递归核验来源案件资源，因此必须分清正在结案的会话与原退款所在会话。见 [B07](B07-人工接管与结案.md)。
