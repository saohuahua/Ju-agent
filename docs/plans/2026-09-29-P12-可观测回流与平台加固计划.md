# P12 可观测回流与平台加固计划

制定日期：2026-09-29

来源：[Agent 工程与平台功能补充调研](../research/2026-09-29-agent工程与平台功能补充调研.md) 选定的四个工作项。本文档是实施计划，不是调研结论的重复。

## 背景与目标

调研确认四项缺口按用户决策排期：Agent 方向两个 P0（OTel GenAI 导出、trace 转评测用例），常用功能两个 P0（限流与请求级超时、会话生命周期）。四项共同点：全部离线可验证、不依赖真实模型调用、不引入外部服务。

完成后的对外表述变化：

- 「事件表是私有格式」→ 「任意会话可导出为符合 OTel GenAI 语义约定的 OTLP JSON，自带离线校验器」
- 「坏例回流是手工过程」→ 「一条命令从历史 run 生成 L1 用例草稿，显式采纳后入回归集」
- 「无限流无请求级超时」→ 「按身份与端点分级的内存限流与超时，429 可复现」
- 「awaiting_input 会话永不过期」→ 「空闲会话确定性收尾，幂等可回放，不触碰在途资金」

## 范围与非目标

### 范围内

1. 新包 `packages/telemetry`：事件表到 OTLP JSON trace 的映射器与校验器
2. CLI `trace:export` `case:from-run` `case:adopt` 及脚本
3. 契约变更：`EVAL_CATEGORIES` 增 `regression`、事件类型增 `run.expired`
4. API 限流与请求级超时中间件（自写，零新依赖）
5. 会话空闲 TTL 收尾服务与扫描器
6. 全部配套测试、文档、交接记录

### 非目标（本轮明确不做）

- OTLP gRPC 上报、collector、Langfuse 等外部平台接入实测
- 限流的分布式实现（Redis）、按 IP 维度、管理界面
- 站外提醒通知（过期前发提醒属于后续站外通知 P1）
- L2 scenario 自动生成、fixture patch 自动推断
- escalated / handling_human 会话的人工侧 SLA（属 0928 调研坐席体系方向）
- build、Docker、真实模型调用、真实支付

## 已在本轮计划中核实的代码事实

实施前不必重新调查，证据均为本轮源码读取：

- 脚本模型 step 有五种 kind：`tool_call` `clarify` `action` `final` `escalate`（[scripted-model.ts](../../packages/agent/src/scripted-model.ts) L27-37）
- SSE 终态判定已含 `cancelled`（[app.ts](../../apps/api/src/app.ts) L709-714 `isRunTerminal`）
- 状态机允许 `awaiting_input → cancelled`（[enums.ts](../../packages/contracts/src/enums.ts) RUN_TRANSITIONS）
- `end_consultation` 收尾为 `completed` + `run.completed` 事件，前置守卫为 awaiting_input、无未完成 p6 任务、无退款关联、toolVersion 为 customer-guidance-v1（[conversation-journal.ts](../../packages/persistence/src/conversation-journal.ts) control）
- 每次模型调用的 token 用量在 `p7_calls.usage_json`，状态 held/unknown/settled（[p7-migration.ts](../../packages/persistence/src/p7-migration.ts)）
- `tool.completed` 事件自带 `latencyMs` `status` `errorCode`；`tool_executions` 表自带 `latency_ms` `attempt`
- `context.compacted` 事件含 strategy 与前后 token，对应 OTel `gen_ai.conversation.compacted`
- hono 4.6.14，无内置限流中间件，按项目零新增依赖惯例自写
- 本地离线业务库路径 `data/local-offline/business/app.db`（[local-offline-paths.ts](../../scripts/local-offline-paths.ts)）

## 阶段 0：剩余 spike（半天）

1. **事件时间戳精度**。读事件写入处确认 `created_at` 是否毫秒级 ISO。若只到秒，span 时长一律取事件内显式字段（`latencyMs`）而非时间戳差，时间戳仅做排序与跨度下界
2. **messages 端点同步性**。确认非持久会话（旧路径）的 POST /api/runs/:id/messages 是否同步跑完模型轮。决定该端点超时阈值（同步路径 120s 与模型轮重试上限对齐，异步 202 路径 30s）
3. **eval 包路径解析惯例**。adopted JSON 用例文件的加载位置与解析方式，跟随 eval/reports 的现有做法
4. **L1 baseline 夹具与本地 demo 夹具差异**。决定 draft meta 的人工核对提示文案，不追求自动生成 fixturePatch
5. **web 端 EventSource 重连行为**。确认服务端主动关闭流后浏览器自动重连并带 Last-Event-ID（SSE 生命周期收尾依赖此行为）
6. **cancelled 终态的评分与看板口径**。检查 rating 与 analytics 对 cancelled 的现有处理，收尾后无需改动的则记录，需要补的列入阶段 4

## 阶段 1：A1 OTel GenAI 导出

### 设计

新包 `packages/telemetry`，只依赖 contracts 与 persistence（纯读侧，不依赖 runtime）：

```
packages/telemetry/src/
  index.ts        导出公共 API
  otlp.ts         OTLP JSON trace 结构的 zod schema（手写 不引入 SDK）
  trace-id.ts     runId 到 traceId/spanId 的确定性派生
  mapper.ts       事件表 + tool_executions + p7_calls → spans
  validate.ts     交叉核对不变量
```

**span 映射表**（对齐 [OTel GenAI Spans 约定](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)，规范状态 Development，按 2026-09-29 快照实现）：

| 源数据 | span | 关键属性 |
| --- | --- | --- |
| 整个 run | root span `run <runId>` | `gen_ai.conversation.id`、`gen_ai.prompt.name`/`version`（run.started）、`gen_ai.request.model`（agent_runs.model）、source/customer 自定义属性 |
| 每条 p7_calls | `chat <model>`（CLIENT） | `gen_ai.operation.name=chat`、`gen_ai.usage.input_tokens`/`output_tokens`（usage_json）、`gen_ai.response.finish_reasons`（agent.turn 的 stopReason）、`gen_ai.conversation.compacted`（该调用前是否发生过压缩）、attempt、status（held/unknown/settled 映射 span status） |
| 每条 tool_executions | `execute_tool <toolName>`（INTERNAL） | `gen_ai.tool.name`、attempt、`error.type`（error_code）、duration 取 latency_ms |
| context.compacted | 挂在相邻 chat span 的 span event | strategy、before/after tokens |
| guard.blocked、tools.catalog_changed | span event 挂到时间上最近的父 span | layer、action、visible/gated |

时间戳：chat span 用 p7_calls.created_at/settled_at 与 agent.turn 事件；工具 span 用 tool_executions.created_at + latency_ms。若阶段 0 确认事件时间只到秒，全部 duration 以显式字段为准并在文档注明。

**校验器不变量**（validate.ts，全部确定性断言）：

1. 结构通过 otlp.ts 的 zod schema
2. 每条 settled 且有 usage 的 p7_calls 恰好对应一个 chat span，token 数值一致
3. 每条 tool_executions 恰好对应一个 execute_tool span，latency/status/error 一致
4. 子 span 时间均在 root span 范围内
5. tool.requested 事件数（按 attempt 展开）与 execute_tool span 数一致
6. traceId 全 trace 一致且可由 runId 重算

**CLI**：`scripts/trace-export.ts`，package.json 增 `"trace:export": "tsx scripts/trace-export.ts"`。参数 `--run <runId> --db <path> --out <file>`，db 缺省 `data/local-offline/business/app.db`，out 缺省打印 stdout。导出后立即跑校验器，失败非零退出。

## 阶段 2：A2 trace 转评测用例

### 设计

**生成器** `packages/eval/src/trace-extract.ts`，纯函数：事件列表 + agent_runs 记录 → `{ meta, case: EvalCaseInput }`。

映射规则：

- `turns`：按序取 `message.user` 的 text（含补答回复，requestKey 字段丢弃）
- `modelScript`：按 agent.turn 顺序，每个 tool_use block → 对应 kind 的 step（只读工具 → `tool_call`，ask_user → `clarify`，动作工具 → `action`，escalate → `escalate`），末条 assistant 文本 → `final`（answer 取 message.completed，escalated 与 summary 按终态填）
- `actor`：从 agent_runs.customer_id
- `frozenTime`：agent_runs.created_at（保证政策窗口判定可复现的关键字段）
- `fixture`：'baseline'，meta 标注需人工核对夹具差异
- `assertions`：初稿只生成确定性部分——expectedState（run 终态）+ trajectory（requiredTools 取实际调用去重，maxToolCalls 取实际值加余量）；communicateInfo 与 judgeRubric 留空由人工补
- `id`：草稿阶段占位 `draft_<runId>`，采纳时强制显式指定

**meta**：`{ sourceRunId, generatedAt, promptVersion, model, sessionSource, needsReview: ['fixture', 'communicateInfo', 'expectedState'] }`。

**两步命令**，边界保证「禁止无审查自动入库」：

1. `pnpm case:from-run -- --run <runId> [--db <path>]` → 写 `eval/traces/<runId>.draft.json`（目录加入 .gitignore），只生成不触碰用例集
2. `pnpm case:adopt -- --draft <file> --id <caseId> [--priority P1]` → 校验 draft 的 case 部分通过 EvalCase 契约后，复制到 `eval/cases/regression/<caseId>.json` 并登记

**契约变更**：`EVAL_CATEGORIES` 增 `'regression'`（[eval.ts](../../packages/contracts/src/eval.ts) L12）。`packages/eval/src/cases/regression.ts` 新建，按现有数据文件加载惯例读取 `eval/cases/regression/*.json` 并经 validateCases 同样校验，注册进 EVAL_CASES。category 计入优先级统计与 dataset 导出。

**重放一致性**：采纳的用例跑 `pnpm eval -- --case <caseId>` 必须通过，因为 modelScript 即原行为重放。若原会话是坏例，人工修改期望后再采纳，修改内容进 handoff 记录。

### 验收（DoD）

- [ ] 对一条正常完成的模拟会话生成 draft，case 部分通过 zod 契约校验，meta 字段齐全
- [ ] adopt 后 L1 单用例重放通过（与原终态一致）
- [ ] adopt 无 --id 显式参数即失败，不存在任何自动入库路径

## 阶段 3：限流与请求级超时

### 设计

自写中间件，两个文件：`apps/api/src/rate-limit.ts`、`apps/api/src/request-timeout.ts`。零新依赖，单进程内存实现（与单节点单写者架构一致）。

**限流**（固定窗口，按 actor 键：customer 取 customerId，operator/supervisor 取角色）：

| 端点组 | 窗口 | 上限 |
| --- | --- | --- |
| POST /api/runs（建会话） | 每客户每分钟 | 5 |
| POST messages / resume | 每客户每分钟 | 12 |
| 坐席写接口（handover、operator-messages、resolve、decide、logistics-events、operations） | 每角色每分钟 | 60 |
| POST /api/eval/run、run-sim | 每角色每分钟 | 2 |
| 其余 GET | 每 actor 每分钟 | 240 |
| SSE GET events | 每 actor 并发数 | 4 |

- 命中限流：429 + `{error:'RATE_LIMITED'}`（复用现有错误码映射）+ `Retry-After` 头
- 拦截记结构化日志（JSON line：actor、route、window、limit），不写库不写事件流，保持热路径零额外写入；测试经注入 logger 断言
- /api/health 与 /api/ready 豁免
- 窗口计数器暴露简单的运行时快照函数供测试

**请求级超时**：

- 同步跑模型轮的端点（阶段 0 确认具体清单）：120s，与 MODEL_TURN_ATTEMPTS 重试上限对齐；超时返回 503 + `{error:'REQUEST_TIMEOUT'}`，正在执行的模型调用经 AbortSignal 取消
- 异步受理端点（持久会话 202 路径）：30s
- SSE 流：增加最大存活时长（默认 15 分钟）到期优雅关闭。客户端 EventSource 自动重连带 Last-Event-ID，由既有补发能力无损恢复；关闭前写入 `: server-refresh` 注释帧提示

**阈值配置**：常量集中在中间件文件顶部，env 覆盖（`RATE_LIMIT_*`、`SSE_MAX_LIFETIME_MS`），默认值写入手册。

### 验收（DoD）

- [ ] 压测脚本（vitest 集成测试内多次调用）触发 429，响应含 Retry-After，且下一窗口恢复
- [ ] 限流不破坏更深层防线：请求键去重、幂等命令在限流之外的行为不变（专项回归）
- [ ] 同步端点超时返回统一错误结构，中断的模型调用不落半截事件（复用既有流中断语义）
- [ ] SSE 到期关闭后测试模拟重连，Last-Event-ID 补发无丢失
- [ ] L1 全量 124/124 不受中间件影响（评测路径豁免或限额足够，以实测为准并在 handoff 记录选择）
- [ ] 全量 test / typecheck / lint 全绿

## 阶段 4：会话生命周期

### 设计

新增 `packages/domain/src/services/session-expiry-service.ts` + API 进程内扫描器。

**规则**：

- 目标：`status='awaiting_input'` 且 `source='customer'` 且 `updated_at < now - TTL`
- TTL 默认 72 小时，env `SESSION_IDLE_TTL_HOURS` 覆盖
- 守卫（逐条在事务内复查）：无未完成 p6 任务（queued/running/needs_confirmation）、无退款关联（P6ConversationRefundRepository.link 为空）。在途资金（awaiting_approval）不在目标集合，结构性不触碰
- 收尾动作：`RunService.transition(runId, 'cancelled')`（CAS 保证并发只有一个成功）+ 追加新事件

**契约变更**：EVENT_TYPES 增 `run.expired`，payload `{ reason: 'idle_ttl', idleHours: number, lastActiveAt: string }`。同步点：

- `customer-view.ts` 公开事件白名单加入 `run.expired`，客户侧可见「会话已因长时间无回复自动结束」
- web 端 runReducer / customer-messages 处理该事件类型，渲染收尾提示
- SSE 终态判定无需改（cancelled 已在列表）
- `run.expired` 不参与任务成败判定，运营看板按既有 source 口径自然排除过期会话的新增活动

**扫描器**：API 启动时扫一次 + 每 10 分钟周期扫描（setInterval，注入 Clock 便于测试）。批处理 LIMIT 100 逐条走领域服务，失败单条记日志不阻塞批次。多进程部署下 CAS 迁移保证幂等，重复扫描只是空转。

**收尾后体验**：客户在已过期会话发消息 → journal.offer 的 awaiting_input 校验返回 409「会话不在等待补充信息」→ 前端提示新建咨询（既有入口）。验收时确认 409 文案可理解，必要时补前端映射。

**与新版引导会话的关系**：客户主动结束走既有 `end_consultation`（completed + run.completed），系统过期走本服务（cancelled + run.expired），两条路径语义分离互不复用，避免把系统行为伪装成客户动作。

## 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 事件时间戳精度不足 | span 时长失真 | 阶段 0 确认；duration 一律取显式字段（latencyMs），时间戳仅作排序，文档注明 |
| OTel 约定仍在 Development | 规范变动 | 代码内注明快照日期与版本，schema 集中在 otlp.ts 一处，变动只改一处 |
| scripted-model 脚本与真实多轮轨迹切分不对齐 | 生成的用例重放失败 | 阶段 2 首个任务写「轨迹→脚本」单测对齐五类 kind；不对齐处先修生成器不迁就格式 |
| baseline 夹具与导出会话数据不一致 | 采纳用例误判 | meta.needsReview 强制人工核对；diff 工具属非目标，宁慢勿错 |
| 限流误伤评测与既有测试 | L1 假失败 | 评测入口豁免或限额充足二选一，实测后把选择写进 handoff |
| 过期收尾与挂起物流事件交互 | 丢触达 | 挂起事件留在事件流作为历史事实，触达窗口已过不再补发，边界写入 handoff |
| cancelled 会话的评分与看板口径 | 统计口径混乱 | 阶段 0 核查 rating/analytics 对 cancelled 的现状，需要补口径的在阶段 4 一并处理 |
| modelScript kind 'action' 槽位语义复杂 | 草稿字段错误 | action 步骤生成时从 agent.turn 的 tool input 原样复制槽位，不做推断 |
