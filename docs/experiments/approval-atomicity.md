# 审批原子性实验

日期：2026-09-25

## 要验证的问题

两位主管同时对同一申请给出不同决定时，最终只能保存一个决定。

两条执行路径同时出示同一审批令牌时，最多一条取得执行授权。审批已被消费后的空字符串必须无效。

HTTP 已受理审批决定后，即使后续内存调度没有开始，也应留下可查询的执行意图。

## 原实现的失败窗口

原服务先读 pending，再调用仅按 approval_id 更新的 SQL。两个请求可以同时读到 pending，之后各自覆盖状态，返回各自成功。

原令牌消费先读再把字段置空，没有在 UPDATE 中比较旧令牌。更严重的是，后续传入空字符串可能与已清空字段相等，重新获得授权。

这两个问题都不能用进程内 Map 或页面按钮禁用来解决，因为不同连接或进程不共享该内存状态。

## 现在的机制

### 审批决定

仓储只暴露 decidePending 与 consumeToken，不再提供通用审批整行更新。

决定写入同时检查待审批状态和有效期。HTTP 路径还检查运行归属、awaiting_approval 状态和核验时的最新断点编号。

API 在写入前比较审批与断点中的申请标识、业务资源类型、资源编号和金额。数据库事务使用断点编号进行再次校验，防止核验后出现新的处理方案。

UPDATE 返回的行决定是否成功。没有更新到行时，领域服务重读当前审批，区分已决定、过期和前置条件冲突。

### 一次性令牌

消费 SQL 同时比较申请标识、资源类型、资源编号、approved 状态、非空原令牌和有效期。

只有受影响行数为 1 才返回授权成功。消费接口不能修改审批状态，也不能把令牌写回来。

### 执行意图

HTTP 路径在同一 SQLite 事务中写入决定和 approval_execution_intents。

意图使用 approval_id 作为唯一键，状态为 pending、running、completed 或 failed。认领通过 pending 到 running 的条件更新完成。当前不允许自动重新认领 running。

completed 表示本次恢复调用结束，不表示所有业务资金已经成功。例如恢复后等待客户补充时，恢复调用已结束，但案件尚未办完。

普通领域评测仍直接调用审批服务并同步驱动工作流，没有因此被包装成持久任务系统。

## 实验与结果

运行入口：

```powershell
pnpm --filter @aftersales/persistence test
pnpm --filter @aftersales/workflow test
pnpm --filter @aftersales/api test
```

持久化专项文件：packages/persistence/test/approval-concurrency.test.ts

| 场景                     | 实际断言                                           |
| ------------------------ | -------------------------------------------------- |
| 两连接先读取再争抢决定   | 一个 decided，一个 already_decided，只产生一个意图 |
| 两连接争抢同一令牌       | 一个成功，原令牌重放与空令牌都失败                 |
| 错角色、错案件、状态变化 | 拒绝修改审批，不生成执行意图                       |
| 错资源或到期             | 不能消费令牌，原凭据保持原值                       |
| 核验后断点改变           | 条件更新返回空，审批仍 pending                     |
| 注入意图写入失败         | 决定与意图同时回滚                                 |
| 关闭连接后重新打开磁盘库 | pending 意图仍存在，只能被认领一次                 |
| 两连接同时接管           | 一个成功，只写一条接管事件                         |
| 工作流收到伪造批准参数   | 未批准或真实决定不符时不执行资金动作               |
| 同一运行中的错误方案     | API 返回 409，审批和意图均未变化                   |

竞争用例使用同一磁盘库上的两个独立连接和服务实例，以 Promise.all 形成读后写交错。SQLite 驱动仍在同一 Node 进程执行，这不是两个进程同时竞争数据库锁的实验。

重新打开数据库证明执行意图持久化，不证明 Worker 崩溃后自动恢复。

## 仍未关闭的窗口

| 窗口                         | 当前行为与后续工作                                   |
| ---------------------------- | ---------------------------------------------------- |
| 决定提交后进程退出           | pending 意图可查，自动扫描调度待 P6                  |
| 意图认领后进程退出           | 保留 running，不盲目重新执行，待租约与结果核验       |
| 令牌消费后、渠道调用前退出   | 不恢复令牌，需持久动作授权和业务幂等设计             |
| 渠道成功但本地未记账         | 当前内存模拟网关不足以证明跨进程幂等，待持久渠道实验 |
| 人工接管状态写入后事件前退出 | CAS 防重复接管，不保证事件和状态一起提交             |
| 人工结案但仍有未完成资金记录 | 当前尚未加完整业务终态核验，不得声称 P3 全部完成     |

## 可用于学习的追问

1. 为什么先读状态再更新不能防并发，WHERE 条件需要比较哪些字段？
2. 唯一键为什么不能代替审批状态条件？
3. UPDATE 成功但意图 INSERT 失败时，事务怎样保证两者一致？
4. 一次性令牌只消费一次，为什么还不能证明退款只执行一次？
5. pending 和 running 在重启后为什么不能采取相同重试策略？
6. 为什么本次双连接测试不能写成分布式恢复已经通过？
