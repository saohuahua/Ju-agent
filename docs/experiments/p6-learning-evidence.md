# P6 复盘分析与简历事实材料

日期：2026-09-25

本文从已经运行的实验提取学习与表达材料。数字来源见 [实验记录](p6-recovery.md) 和 [原始数据汇总](p6-results/2026-09-25T14-52-15.247Z/analysis.md)。这不是生产效果报告，也不是已经完成全部主链路接入的项目介绍。

## 一条可以讲清楚的问题链

### 发现问题

旧系统已经把审批决定与执行意图写进同一个数据库事务，但 API 之后仍依赖内存异步函数调用恢复。批准之后进程退出，意图虽然存在，却没有可靠的持久调度去接手。

内存支付 Mock 只能验证同一服务对象的去重，无法证明应用进程重启后外部渠道还记得原交易。单纯将异常 catch 后再调用一次，也无法证明真实崩溃恢复正确。

### 拆分失败语义

请求失败、业务拒绝、业务结果未知是三种不同事实。

响应丢失实验中，HTTP 调用确实失败，但支付渠道已经成功。如果把它写为业务 failed 并让 Agent 重新规划，就可能换一个业务键重复执行。
实验因此把调度状态、业务状态与渠道状态分开记录；未知结果留在 needs_confirmation，恢复只能查询原键。

### 逐层处理

1. 持久受理解决返回 accepted 后内存任务丢失的问题，唯一请求键解决客户端重试。
2. 原子认领解决双 Worker 竞争，租约解决死进程长期占用，代次解决旧进程迟到覆盖。
3. 检查点记录已确认模型和只读步骤，恢复不用从头调用模型。
4. 资金业务键绑定业务资源而非 runId，避免新运行编号绕过去重。
5. 独立渠道记录真实模拟交易，本地落库空窗依赖渠道查询和事务回写收敛。
6. 通过独立子进程在指定边界退出，保存日志与两个数据库，验证的对象是崩溃后的持久事实。

### 观察结果

- 支付成功但响应丢失后，渠道仍只有一次 POST 和一个成功动作，恢复通过一次查询确认
- 支付成功但本地未记账后，新 Worker 的 generation 增加，本地业务和幂等记录补齐
- 已保存模型检查点后退出，恢复日志只有一次模型调用
- 模型文本流中途退出，重新调用模型，但资金动作没有重复
- 两个 Worker 同时认领只有一个成功，过期旧 Worker 的检查点写入与续约均被拒绝
- 新 runId 对同一业务动作建立第二个任务，渠道仍只发生一次成功动作
- 真实 SSE 连接断开后使用游标重连，已确认的第一条事件不重复，后续两条事件没有遗漏

## 不能回避的取舍

### 安全与自动恢复率

发送意图已落库但实际请求还未发出时退出，重启查不到交易。系统仍不自动发送。
从夹具视角知道这次 POST 为零，但真实系统不能据一次 not_found 排除在途请求或渠道可见性延迟。保守等待减少自动恢复率，却避免依据不充分时重放资金。

如果未来渠道提供有证明力的未受理终态、持久幂等承诺和明确的重发契约，才可以对特定分支放开同键重试。当前没有这样的真实渠道证据。

### 本地事务与外部副作用

SQLite 事务不能包住外部支付服务，也不能因 HTTP 超时回滚已经发生的支付。
所以不能声称实现全链路 exactly once。准确表述是本地原子受理与围栏写回，加业务幂等键、外部结果查询和保守核验，在已测试故障窗口下避免重复已确认动作。

### 检查点与模型成本

检查点之后崩溃可以跳过已确认调用；模型完成但检查点尚未提交时仍可能重复调用模型。该调用是否计费属于 P7，不应因本地结果丢失就按零费用处理。

### 取消与退款

取消长任务意味着停止后续工作，不意味着撤销已经发生的资金动作。
实验中存在 cancelled 任务对应 succeeded 补偿的合法组合。系统需要把这个组合解释清楚，而不是覆盖资金终态来满足界面上单一的取消标签。

## 如何分析下一次失败

按以下顺序核对，避免看到异常就加重试。

| 问题                  | 先看证据                      | 再判断                             |
| --------------------- | ----------------------------- | ---------------------------------- |
| 是否真正受理          | p6_commands 和 p6_tasks       | 返回值是否发生在事务提交之后       |
| 是否存在有效所有者    | owner generation lease_until  | 旧进程是否还在写回                 |
| 哪一步已经确认        | p6_steps 和 p6_events         | 是否错误地重跑已完成步骤           |
| 资金是否可能发出      | p6_effects 的发送状态         | 是否必须先查询原业务键             |
| 渠道是否确认终态      | channel.db 与查询日志         | 拒绝 超时 未知是否被混为一谈       |
| 本地是否完成记账      | 业务单 幂等表 审计 支付检查点 | 本地事务是否整体回滚或整体提交     |
| 新 runId 是否绕过去重 | 两个命令的 businessKey        | 键是否错误地包含运行编号           |
| 模型是否重复调用      | process.log 中 model-called   | 重复的是未确认调用还是已确认步骤   |
| 客户是否丢失进度      | 两份 SSE 原文与事件 cursor    | 是服务端漏发还是客户端没有保存游标 |

复盘时先抄出事实，再写原因假设，最后设计能推翻该假设的测试。不要用一次通过的夹具结果直接宣称真实环境普遍正确。

## 简历中可以使用的事实表述

以下表述仅对应当前独立模块成果，正式接入完成后才能去掉范围限定。

> 为售后 Agent 实现独立的持久任务与恢复模块，基于 SQLite 事务完成命令幂等受理、Worker 原子认领和租约代次隔离，并通过检查点续跑避免重复已确认步骤。

> 搭建独立进程与独立数据库的本地支付模拟渠道，区分调用失败、业务拒绝和结果未知；通过业务幂等键与结果查询验证响应丢失、支付成功但本地未记账及跨运行重复执行等故障窗口。

> 编写 42 条 P6 专项测试，其中 18 个进程及渠道故障场景与 1 个真实 HTTP SSE 断连重连场景，保存进程日志、数据库终态、源码摘要与自动汇总报告，形成可复盘的工程证据。

前两条适合简历项目要点。第三条数字较密，适合项目文档或面试补充；如果写入简历，必须保留“本地模拟”和“独立模块”的范围。

## 面试中值得追问的六个问题

1. 为什么请求幂等键与支付业务键不能共用 runId
2. 为什么只有租约还不够 旧 Worker 返回时如何防止覆盖
3. 为什么支付查不到记录时仍然选择待核验
4. 为什么检查点不能独自解决外部副作用的重复执行
5. 为什么取消任务之后业务记录仍可能是资金成功
6. 怎样证明测试真的跨进程 而不是在同一对象上捕获异常再重试

回答时先给具体实验，再解释机制，最后说明边界。能够解释保守失败和未完成部分，比只背幂等与事务术语更有说服力。
