# 业务背景 为什么做电商售后 Agent

本文说明项目的业务动机与宏观判断 是面试讲清"为什么做这个"的底稿

## 售后在电商平台中的位置

电商交易的完成不是签收而是售后闭环结束 从平台视角售后链条同时消耗三类资源

- 资金 退款占用与差错成本 一次重复退款是直接资金事故
- 人力 客服处理工时 大促期间售后量是平时数倍 峰值人力最贵
- 体验 逆向物流的等待与扯皮直接影响复购与店铺评分

售后处理的本质是三种动作的组合 信息检索 订单与物流 政策判定 规则窗口与类目
副作用执行 退款 改单 前两类占工时的大头且高度结构化 第三类风险最高但频率最低

## 为什么全人工不可持续

- 政策规则多 七天无理由与质量问题窗口不同 类目排除不同 运费承担方不同 人工记忆与执行不一致
- 重复劳动 查单 查物流 解释政策占大部分工时 熟练度提升空间极小
- 人为差错 旺季高压下的重复退款 漏审批是真实事故来源

## 为什么全自动不可行

- 例外场景真实存在 超时但客户有理由 情绪安抚 欺诈嫌疑 这些需要人的判断
- 副作用风险 退款是不可逆动作 判定模型一旦出错 无法用道歉挽回
- 监管与信任 高金额与例外操作保留人工把关 既是风控要求也是客户信任基础

## 本项目的人机分工设计

按风险分级切分自动化边界

| 动作类型             | 风险 | 处理方                    | 系统保障            |
| -------------------- | ---- | ------------------------- | ------------------- |
| 查单 查物流 政策解释 | 低   | Agent 自动                | 只读工具 白名单     |
| 创建售后单 政策判定  | 中   | Agent 自动 确定性政策引擎 | 状态机 审计         |
| 普通金额退款         | 高   | Agent 发起 工作流执行     | 幂等键 网关去重     |
| 大额 例外退款        | 高   | 人工审批                  | 一次性令牌 审批超时 |
| 例外与纠纷           | -    | 升级人工                  | 升级留痕            |

这个设计的核心判断是 Agent 的价值不在对话 在受控地完成有副作用的业务闭环
模型负责理解和异常路径 确定性代码负责资金安全 两者缺一不可

## 这个场景对评测的天然优势

1. 业务终态可断言 退款金额 状态 审计记录都在数据库里 不需要主观打分
2. 轨迹可验证 哪些工具必须调用 哪些禁止调用 参数对不对 都有明确答案
3. 故障可注入 超时 限流 进程中断都可以确定性模拟 恢复能力可量化
4. 攻击可演练 越权与提示词注入有明确预期行为 防御率可计算

这正是调研里选择售后而不是通用客服的原因 客服问答没有副作用 也就无法证明可靠性

## 指标体系

评测看板输出的指标直接对应业务语言

- 任务成功率 TSR 自动化率的上界 前提是无违规无重复副作用
- 政策违规率 资金安全底线
- 重复副作用率 幂等有效性 资金事故率的核心构成
- 断点恢复成功率 系统韧性
- 注入防御率 安全底线
- Pass^3 稳定性 生产 Agent 不能靠运气 多次运行全过才算过

## 边界与诚实

- 业务数据是构造夹具 不代表真实分布 真实迁移需要真实数据回放
- 政策规则是简化版六个规则 真实平台政策面大一个数量级
- 支付网关是幂等 mock 演示的是治理机制 不是渠道对接能力
